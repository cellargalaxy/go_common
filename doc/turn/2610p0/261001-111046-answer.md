## 二、现状核对结论（历史资料 × 当前代码，发现 4 处必须修正的事实）

1. **msg_gateway 依赖的 3 个 go_common API 已不存在**（已 grep 全仓确认命中数为 0）：
   - `util.GetLogIdString(ctx)` → 当前只有 `util.GetLogId(ctx) int64`（`util/log.go:122`），需配 `util.Int2Str`
   - `util.GetIp()` → 当前为 `util.GetIP()`（`util/http.go:206`，大写 IP）
   - `LocalCache.GetWithTimeout(...)` → 当前为 `LocalCache.Fetch(ctx, key, duration, get)`（`util/cache.go:92`）
   结论：历史 SDK 代码**不可直接搬运**，必须按当前 util 的 API 重写。

2. **业务错误被静默吞掉（现状缺陷）**：`sdk/template_message.go` 的 `sendTemplateMessage` 只判断 Go 层 `err`，而 PowerWeChat 在 `baseClient.go:505-571` 中只把 errcode 用于「是否刷 token 重试」，**errcode≠0 时 `err` 仍为 nil**。因此「模板 ID 错误 / 未关注 / 超配额」这类失败在现状下既不报错也不打日志，表现为「消息没到但一切正常」。新方案必须显式校验 `ResponseOfficialAccount.ErrCode`。

3. **重试策略放大故障**：现状 `ReTry`（`sdk/sdk.go:62`）固定 5 次、间隔 5 秒、仅按 `err != nil` 重试。叠加问题 2，真正该重试的业务错误不会重试；而一旦是网络抖动，调用方最坏被**同步阻塞 25 秒**。

4. **接收人靠 env 枚举**：现状 `GetUsers()`（`sdk/sdk.go:21`）读 `wx_user` 逗号分隔 openid，`SendTemplateData` 对其逐个发送。即「全发给配置里列出的人」，并非「发给我自己」——本轮要解决的正是把这项配置去掉。

## 三、核心目标与范围边界

**目标**：在 `go_common/util` 中提供一个**零配置可用、旁路、不可失败传染**的「发一条通知到我微信」的能力，替代 msg_gateway 整个仓库。

**范围内**：
- 把「一段正文文本（可多行）」投递为公众号模板消息，落到我自己的微信。
- 自动解析接收人与模板，调用方不需要知道 openid、template_id、模板标题。
- 配额保护、失败可观测、未配置时静默降级。

**范围外（明确不做）**：
- 不保留 msg_gateway 的「网关」形态：不做 HTTP 服务、不做消息队列、不做持久化重投。
- 不做消息路由/多模板/多渠道抽象（只有一个通用模板、一个接收人，抽象是净负债）。
- 本轮不把该能力挂到 `logrus` Hook 上做自动告警（见第八节「递归风险」）。

**关键约束**：
- `go_common` 是被所有项目引用的基础库，**绝大多数使用方不会配置微信**。因此该能力必须是「可选插件」语义：未配置时不 panic、不刷日志、不在 `util.Init()` 里强制初始化（延续现状的懒初始化思路，`sdk.go:54` `GetSdk`）。
- 用户诉求是**降低代码与配置复杂度**，一切「为通用性而生的抽象」都要让位于「为唯一真实场景而生的直路」。

## 五、接收人判定 —— 本轮核心问题

### 5.1 问题本质

「只有一个关注者时，这个关注者就是我」是**事实**（可由 `User.List` 的 `Total/Count` 直接判定）。
但「多个关注者中哪个是我」**不是任何接口能告出来的事实**——关注时间、列表顺序、备注名，全都是*约定*，不是*数据*。按本轮约束「严厉禁止猜测业务逻辑」，代码不应当去猜。

### 5.2 候选方案比较

| 方案 | 判定机制（依据） | 额外 API | 零配置 | 多关注者时是否仍精确 | 风险 |
| --- | --- | --- | --- | --- | --- |
| **A 全部关注者都发** | `User.List` 分页取全部 `Data.OpenID`，逐个发送 | 0 | ✅ | ❌ 退化为广播 | 内部信息（sn/ip/logid/正文）扩散；配额 ×N |
| **B 发给最早关注者** | 对每个 openid 调 `User.Get` 取 `SubscribeTime`（字段确认存在于 `responseGetUserInfo.go`），取最小 | N 次/缓存周期 | ✅ | ⚠️ 取决于「我最先关注」这一前提 | 我若取关再关注，`subscribe_time` 刷新，规则失效；前提无法自证 |
| **C 按备注名匹配** | `User.Get` 返回 `Remark`；`User.Remark()` 可写入约定值 | N 次/缓存周期 | ⚠️ 配置搬到微信侧 | ✅ 稳定显式 | 需一次人工/脚本操作；忘了设置就退化；测试号是否允许 `updateremark` **待确认** |
| **D env 白名单** | 直接读 `wx_open_id` | 0 | ❌ | ✅ | 与「简化配置」诉求冲突 |
| **E 首次自举 + 本地固化** | 首次见到 `Total==1` 时把 openid 写入本地文件，之后恒定使用 | 0（命中后） | ✅ | ✅ | **不推荐**：引入本地状态文件 + 「首次运行时刻必须只有我一个关注者」的时间窗依赖；多机/多进程各自固化；复杂度不降反升，收益不如直接写一次 env |

### 5.3 推荐方案：**A 为默认主路，D 为逃生门，多关注者只升级日志等级、不改变行为**

判定链（优先级从上到下）：

1. `wx_app_id` / `wx_secret` 任一为空 → **静默降级**，不发送，仅一条 Debug 级日志（基础库默认形态，不污染日志）。
2. `wx_open_id` 已配置 → 直接作为接收人集合，**不调用 `User.List`**。
3. 否则调用 `User.List`（分页至 `NextOpenID` 为空），结果缓存：
   - `len == 1` → **该 openid 断定为我自己**，发送。（这是用户给定的事实，也是唯一有数据支撑的断定）
   - `len == 0` → 不发送 + Error 日志（提示「测试号尚无关注者」）。空列表**不进缓存**，避免空结果被缓存住。
   - `len > 1` → **发送给全部关注者**，同时打一条 Warn：「检测到 N 个关注者，当前为广播行为，建议配置 `wx_open_id` 限定接收人」。

**为什么这是「简洁且优雅」的答案**：
- 默认路径对「只有我自己关注」这一真实场景优化到极致：零配置、零推断、零额外判定逻辑。
- 多关注者不被当作「需要猜测的歧义」，而被当作**配置缺失的信号**：代码不猜，只把决策权连同可执行建议交还给人。
- 可用性优先：通知/告警链路宁可「多发给了别人」也不要「静默不发」——因为静默失败会让这条链路在最需要它的时候失效。
- 升级路径是一行 env，不是一次改码。

**需用户确认的取舍点**（见第十二节）：若认为「宁可不发也不能外泄内部 IP/正文」，则把 `len > 1` 的行为从「广播 + Warn」改为「不发送 + Error」。这是同一判定链上一个分支的差别，不影响其余设计。

## 六、模板判定

1. `wx_template_id` 已配置 → 直接使用，不调 `GetPrivateTemplates`。
2. 否则调 `GetPrivateTemplates`，结果缓存：
   - `len == 1` → 用它。（与「只配置了一个通用模板」的事实完全对齐，零配置）
   - `len == 0` → 不发送 + Error 日志；空结果不进缓存。
   - `len > 1` → 不发送 + Error 日志，提示配置 `wx_template_id`。
     **不做猜测性兜底**（不取第一个、不按标题硬编码匹配）：用错模板必然被微信以 errcode 拒绝，且会白白消耗配额。
3. 可选增强（本轮不纳入主方案，列为备选）：多模板时按 `Template.Content` 中是否同时含 `sn`/`ip`/`logid`/`text` 四个占位符来筛选。这是**从 `Template.Content` 字段可推导**的筛选，不属于猜测；但占位符在 content 中的确切书写形式需实施前用一次真实返回核对。

> 对比现状：去掉了 `"通用消息"` 这个硬编码标题，以及 `GetTemplateIdCache` 的「1 小时 + 5 分钟」双 TTL 补偿（`template_message.go:15-29`）。双 TTL 存在的唯一原因是「空结果被长缓存」，而把空结果直接判为失败后，这个补偿就不需要了。

## 七、字段装配规则（模板 4 个占位符）

目标模板格式（用户给定）：
```
sn: go_common
ip: 114.114.114.114
logid: 06010112211232131
text: 我是正文A
我是正文B
我是正文C
```

| 占位符 | 取值来源 | 边界处理 |
| --- | --- | --- |
| `sn` | `util.GetServerName()`（`util/os.go:30`，可被 env `server_name` 覆盖） | 为空时填占位符 |
| `ip` | `util.GetIP()`（`util/http.go:206`） | **进程刚启动时必为空**：该值由 `initHttp()` 启动的后台协程 `flushIP` 异步拉取（`util/http.go:27,210`）。为空时填占位符，不阻塞等待 |
| `logid` | `util.GetLogId(ctx)` + `util.Int2Str` | 为 0（ctx 未经 `SetLogId`）时填占位符 |
| `text` | 调用方入参，原样保留换行 | 超长时截断并加省略标记（阈值见「待确认」） |

**调用方只提供 `text`（及可选的跳转 url）**：另外 3 个字段完全由 ctx + 进程环境推导，这是相对现状最直观的简化——现状 `SendTemplateText` 需要传 `name`（模板标题）+ `url` + `text` 三个参数，新方案只需 `text`。

**边界共性**：模板消息要求每个占位符都有值，空字符串的行为**待确认**，故统一用占位符（如 `-`）兜底，不把空串交给微信。

## 八、异常、降级与可靠性策略

### 8.1 错误分类与重试（修正现状缺陷 2、3）

- **必须显式校验 `ResponseOfficialAccount.ErrCode`**，而不是只看 Go `err`。依据：`baseClient.go:505-571` 只把 errcode 用于判断是否刷 token，`RetryDecider`（`:574`）仅覆盖 40001/40014/42001。
- **重试白名单制**：只对「HTTP 层网络错误/超时」与「微信系统繁忙类 errcode」重试；参数错误（模板 ID 不对）、接收者未关注、超配额一律**不重试**——重试它们只会加速配额耗尽。具体 errcode 清单实施时对照微信官方《全局返回码说明》逐条确认，不在本轮凭记忆写定。
- **重试参数**：3 次，间隔沿用 go_common `httpClient` 的节奏（`util/http.go:25` 的 `{1s, 2s, 2s}`），复用 `util.Sleep`。相对现状 5 次 × 5 秒，最坏阻塞从 25 秒降到约 5 秒。
- **access_token 自动刷新由 PowerWeChat 内部承担**（`baseClient.go:538` 命中 40001/40014/42001 时 `Token.Refresh` 后重放请求），业务层不重复实现。

### 8.2 同步 vs 异步

推荐**同步执行并返回 error**，由调用方决定是否 `go` 出去。理由：
- 无生命周期管理、无后台队列、无进程退出丢消息，代码量最小；
- 与 `go_common/util` 现有「函数返回 error」的既有风格一致；
- 现状 `SendTemplateText` 无返回值（`template_message.go:66`）会让失败完全不可感知，与缺陷 2 叠加后故障完全隐形。

### 8.3 递归风险（必须隔断）

若后续把该能力挂到 `logrus` 的 Error Hook 上做自动告警，会形成「发送失败 → 打 Error 日志 → 触发发送 → 再失败」的无限递归。
**本轮策略**：只提供显式调用，不接 Hook。若后续要接，隔断手段须在那一轮单独设计（候选：发送路径内部使用不带 Hook 的独立 logrus 实例）。此处仅记录风险，不预先实现。

### 8.4 未配置时的行为

`wx_app_id` / `wx_secret` 缺失是**绝大多数使用方的常态**，不是异常。现状 `InitSdk`（`sdk.go:42`）在参数为空时打 Error 并返回 error——若下沉到 `go_common`，这会给所有未配置微信的项目持续制造 Error 日志。新方案改为 Debug 级静默降级。

## 九、配额保护与去重

测试号的模板消息调用配额有限（具体额度**不可推断**，见第十一节），且本能力的典型使用场景正是「错误发生时发通知」——最容易出现错误风暴打爆配额。

- **相同内容去重**：以正文的 `util.EnMd5Hex` 为 key，复用 `util.LocalCache.TryLock`（`util/cache.go:106`，基于 `cache.Add` 的原子写入）做「同一内容 N 分钟内只发一次」。被抑制的消息打 Info 日志，不报错。
- **去重窗口默认值**：待定（建议 5 分钟量级），应可通过 env 覆盖。
- **全局限流（每小时/每日上限）**：本轮**不做**。理由：在拿到真实配额数字前，任何阈值都是猜的；去重已能挡掉绝大部分风暴。待观察实际消耗后再决定。

## 十、对现有链路 / 性能 / 兼容性 / 下游的副作用

1. **依赖膨胀（需用户知晓）**：`go_common` 当前不依赖 PowerWeChat。引入后将新增 `ArtisanCloud/PowerWeChat`、`ArtisanCloud/PowerLibs`、`ArtisanCloud/PowerSocialite`、`clbanning/mxj/v2`、`redis/go-redis/v9` 等（依据 `msg_gateway/go.mod` 的 indirect 列表）。`gin`/`resty`/`mongo-driver` 与 go_common 现有依赖重叠，增量有限，但 **redis 客户端会成为所有下游项目的传递依赖**，即便它们不用微信。
   - 缓解选项（需用户决策）：放在 `util` 内（最简，符合用户要求）／放在独立子包以便下游按需引入（Go 的 module 粒度下，同 module 内子包仍会进 go.sum，仅减少编译期链接，收益有限）。

2. **access_token 竞争（msg_gateway 废弃后新增的风险）**：公众号 access_token 是 AppID 级全局凭证。msg_gateway 作为单一网关进程时天然只有一个持有者；下沉到 `util` 后，**每个引用 go_common 并配置了微信的进程都会独立获取 token**，而 PowerWeChat 默认缓存是进程内内存（`interactWithCache.go:59` `createDefaultCache`）。
   - **解法（有明确代码依据）**：初始化时设置 `UserConfig.StableTokenMode = true` 且 `ForceRefresh = false`。依据 `officialAccount/auth/accessToken.go:26-33`，此时端点切换为 `cgi-bin/stable_token`；依据 `kernel/accessToken.go:282`，仅在 `ForceRefresh` 为真时才下发 `force_refresh=true`。即多进程各自取 token 而不互相顶掉。
   - 这是相对 msg_gateway 的**必要增量配置**（现状 `sdk.go` 未设置该项）。

3. **PowerWeChat 自带日志体系**：现状把它写到 `/tmp/wechat_info.log`、Level=`error`、Stdout=false（`sdk.go:30-34`）。下沉后应与 go_common 的日志布局对齐（`util/log.go:32` 的 `log/{serverName}/{filename}` 约定），而非写 `/tmp`。

## 三、消息体装配（按对话2 纠正后的单占位符结构）

模板在微信后台只有一个占位符 `{{data.DATA}}`，因此发送请求的 `Data` 退化为单键：`{"data": {"value": "<多行字符串>"}}`（沿用 msg_gateway `template_message.go:81-85` 的 `map[string]string{"value": ...}` 包装形态）。

`data` 的值按固定顺序拼接，前三行为上下文，其后为调用方正文原文：

```
sn: {util.GetServerName()}
ip: {util.GetIP()}
log: {util.Int2Str(util.GetLogId(ctx))}
{正文}
```

| 行 | 来源 | 缺失时 |
| --- | --- | --- |
| `sn` | `util.GetServerName()`（`util/os.go:30`） | 占位符降级，不报错 |
| `ip` | `util.GetIP()`（`util/http.go:206`） | 占位符降级，不报错 |
| `log` | `util.GetLogId(ctx)` + `util.Int2Str`（`util/log.go:122`、`util/transform.go:279`） | 占位符降级，不报错 |
| 正文 | 调用方唯一入参 | **报错**（见第五节） |

**与「入参无法获取有效值则报错」的边界澄清（需确认，第八节第 1 项）**：
`sn`/`ip`/`log` 并非调用方入参，而是函数自动拼接的运行时上下文。其中 `util.GetIP()` 的值由 `initHttp()`（`util/http.go:27`）启动的后台协程 `flushIP`（`util/http.go:210`）异步拉取，**进程启动瞬间必然为空**，且若调用方从未执行 `util.Init()`（`util/util.go:5`）则**永远为空**。
若对这三行也执行「取不到即报错」，结果是**进程启动期与未初始化场景下告警全部失效**，而这恰是最需要告警的时段。因此建议：报错只约束「真正的入参与凭证」（正文、`wx_app_id`、`wx_secret`、解析后的 openid、解析后的 template_id），上下文三行取不到时填占位符继续发送。

**结构性副作用**：四占位符合并为单占位符后，长度压力由四个 value 分摊变为**集中在一个 value**。微信对模板消息单个 value 的长度上限未在代码中体现（见第九节「待确认」），需要在实现中保留截断保护。

## 四、入参解析链（按对话2 决策）

| 项 | 第一优先 | 兜底 | 取不到 |
| --- | --- | --- | --- |
| `wx_app_id` | env `wx_app_id`（`util.GetEnv`，`util/os.go:56`） | 无 | 报错 |

### 4.1 最早关注者的解析

1. `User.List`（`user/client.go:56`，`cgi-bin/user/get`）分页拉取，直到 `NextOpenID` 为空，汇总 `Data.OpenID`。
2. `Total == 0` → 报错「测试号无关注者」。
3. `len == 1` → 直接采用（无需第 4 步，省一次调用）。
4. `len > 1` → 用 `User.BatchGet`（`user/client.go:45`，`cgi-bin/user/info/batchget`）**批量**取回各 openid 的 `SubscribeTime`（`responseGetUserInfo.go` 字段），取最小者。
   - 选 `BatchGet` 而非 N 次 `User.Get` 是为省调用次数；单次批量上限需确认（第九节）。
   - **`SubscribeTime` 相同（同秒关注）时**，以 openid 字典序最小做 tie-break，保证同一环境下行为确定、日志可复现。
5. 解析结果进缓存（`util.LocalCache.Fetch`，`util/cache.go:92`）；**空结果判为失败不入缓存**。

> 不依赖「`User.List` 返回顺序即关注顺序」——该顺序在代码与已读文档中均无依据，属不可推断，故改用 `SubscribeTime` 显式排序。

### 4.2 模板的解析

1. `GetPrivateTemplates`（`templateMessage/client.go:67`）取 `TemplateList`。
2. 空列表 → 报错。
3. 非空 → 取一个（用户指令为「随机」）。
4. 结果进缓存；空结果不入缓存。

**微调建议（待确认，第八节第 5 项）**：改「随机取」为「取列表第一个 + `len > 1` 时打 Warn」。
理由：用户已授权「只会配置一个模板」，`len == 1` 时两者完全等价；差异只在意外出现多模板时——此时「随机」会产生**非确定性行为**（同一环境时而成功、时而因模板占位符不匹配被微信拒绝），属于最难排查的故障类型；「取第一个」则行为稳定、日志可复现，Warn 还能主动暴露「配置与假设不符」。
若希望更强的正确性，可增强为「按 `Template.Content`（`templateMessage/response` 字段）筛选含 `data` 占位符者」——这是从字段可推导的筛选而非猜测，但占位符在 `Content` 中的确切书写形式需实测核对，故不列入主方案。

## 五、重试策略（对话2 核心问题之一）

### 5.1 错误三分层（代码级依据，是整个策略的基石）

| 层 | 判别方式 | 依据 | 处置 |
| --- | --- | --- | --- |
| **L1 传输层** | Go `err != nil`（网络错误、ctx 超时、HTTP 非 200） | `baseClient.go:487` 将非 200 转为 Go error | **本层负责重试** |
| **L2 凭证层** | errcode ∈ {40001, 40014, 42001} | `baseClient.go:574` `RetryDecider` | **不管**：SDK 已自动刷 token 并重放 1 次（`baseClient.go:537-568`）。业务层再叠加重试只会放大请求量 |
| **L3 业务层** | Go `err == nil` **且** `ResponseOfficialAccount.ErrCode != 0` | `kernel/response/wx.go`；`baseClient.go:505-571` 证明 errcode≠0 **不会**转成 Go error | **按码分类**（见 5.3） |

这个「Go err / errcode」二分法是干净的：**凡 Go err 非空即传输层问题，凡 Go err 为空而 errcode 非零即微信业务拒绝**。对话1 已指出 msg_gateway 的核心缺陷正是只看了 Go err 而漏掉 L3。

### 5.2 L1 重试参数

- **次数**：3（1 次首发 + 2 次重试）。相比 msg_gateway 的 5 次（`sdk/sdk.go:62`）收敛。
- **间隔**：`util.SleepWare(ctx, 1s)`、`util.SleepWare(ctx, 2s)`——节奏对齐 go_common 既有 `httpClient` 的 `{1s, 2s, 2s}`（`util/http.go:25`），并自带 ±10% 抖动（`util/math.go:96` `WareNumber`），避免多实例同步重试。相比 msg_gateway 的固定 5 秒间隔，最坏阻塞从约 25 秒降到约 3 秒 + 3 次请求耗时。
- **短路**：每次重试前 `util.CtxDone(ctx)`（`util/ctx.go:46`）检查；`util.Sleep` 本身已响应 `ctx.Done()`（`util/time.go:64-72`）。

### 5.3 L3 分类原则

分类标准是单一的：**重试是否可能改变结果**。

| 类别 | 处置 | 理由 |
| --- | --- | --- |
| 瞬时类（系统繁忙等） | 重试，并入 L1 预算 | 重试可能成功 |
| 配置类（template_id 无效 / openid 无效 / 用户未关注） | **立即失败** | 重试必然得到同一结果，纯浪费 |
| 配额类（接口调用超限） | **立即失败** | 重试会加速配额耗尽，可能延长受限时间 |
| 未知码 | **默认不重试** | 保守：未知码重试的期望收益为负——配置类与配额类在全局返回码中占多数，且后果比「少试一次」更重 |

具体 errcode 清单实施时逐条对照微信官方《全局返回码说明》核定，不凭记忆写死（第九节「不可推断」）。

### 5.4 超时预算：ctx 是唯一真相

这是本轮必须处理的隐患：**取 access_token 的请求没有 client 级超时**。
- `kernel/accessToken.go:67-74` 构造 `helper.Config` 时未设 `ClientConfig.Timeout`；
- `PowerLibs/http/drivers/http/client.go:24-26` 用 `http.Client{Timeout: config.Timeout}`；
- 因 config 非 nil，不走 `ClientConfig.Default()`（`clientInterface.go:24-29`）的 30 秒 → Timeout 实际为 **0，即无超时**。

对同步接口而言，这意味着调用方可能被**无限期阻塞**。唯一兜底是 ctx：已确认 `Dataflow.WithContext`（`PowerLibs/http/dataflow/dataflow.go:70-71`）把 ctx 透传进 `http.Request`，故 ctx deadline 生效。

对应策略：
1. 业务层入口检查 ctx 是否已有 deadline；**没有则自行补一个总预算**（建议 10 秒，覆盖 3 次尝试）。注意 `util.GenCtx()`（`util/ctx.go:26`）基于 `context.Background()`，**无 deadline**，而这正是调用方最常用的 ctx 构造方式。
2. 发送请求侧另有 5 秒默认超时（`baseClient.go:57`），可通过 `UserConfig.Http.Timeout` 显式设定，建议显式设成与总预算匹配的值而非依赖默认。

### 5.5 幂等代价（需决策，第八节第 3 项）

`request.RequestTemlateMessage`（`templateMessage/request/`）只有 `ToUser`/`TemplateID`/`URL`/`MiniProgram`/`Data` 五个字段，**没有任何幂等键**（无 client_msg_id 之类）。因此「请求实际已到达微信、但响应在返回途中丢失」时，L1 重试会**真实产生重复推送**。

这是无法通过设计消除的权衡，只能选边：
- **宁可重复，不可丢失**（推荐）——告警场景下重复消息的代价远低于漏报；
- 或：不重试传输层错误，接受偶发丢失。

## 六、降级策略（对话2 核心问题之二）

前提认知：**本能力只有一个通道，没有备用通道可降**。因此「降级」的真实含义不是切换通道，而是「在哪些点容忍不完整、在哪些点必须失败」。

| 降级点 | 行为 | 理由 |
| --- | --- | --- |
| `sn`/`ip`/`log` 取不到 | 填占位符，继续发送 | 这三行是上下文装饰而非消息本体；`GetIP()` 启动期必空（`util/http.go:27,210`），严格报错会让启动期告警全失效（第三节） |
| 多接收人部分失败（env 配了多个 openid） | **至少一个成功 → 返回 nil；全部失败 → 返回聚合 error** | 告警的目的是触达，不是全量投递审计 |
| 元数据解析失败（openid / template_id） | 立即报错，不降级 | 这是对话2 明确的「入参无法获取有效值则报错」 |
| 最终失败 | 返回 error + 一条 Error 日志，**不落盘、不重投** | 网关形态已废弃；同步语义下重投属于调用方职责 |
| 错误风暴 | 内容去重：以正文的 `util.EnMd5Hex`（`util/codec.go:183`）为 key，用 `util.LocalCache.TryLock`（`util/cache.go:106`，底层 `cache.Add` 原子写入）在窗口内只放行一次；被抑制时返回 **nil** + Info 日志 | 保护测试号配额。抑制是「已经发过了」，不是失败，故不返回 error |

**明确不做**：
- 不做熔断器——状态机复杂度高于收益，内容去重已挡住主要风暴来源；
- 不做本地队列与持久化重投——对话1 已定为范围外；
- 不做多通道兜底——当前只有微信一个通道。

## 七、access_token 竞争的完整处理（对话2 明确要求）

竞争分三个层次，其中**第 3 层是本轮最重要的发现**，它比竞争本身更危险。

### 7.1 跨进程竞争 → stable_token

`go_common` 被多项目引用，msg_gateway 的「单一网关进程持有 token」前提消失后，每个配置了微信的进程都会独立取 token。公众号 access_token 是 AppID 级全局凭证，普通 `cgi-bin/token` 接口刷新会使旧 token 失效。

**解法**：`UserConfig.StableTokenMode = true` 且 `ForceRefresh = false`。
依据：`officialAccount/auth/accessToken.go:26-33` —— `stable_token_mode` 为真时端点切换为 `cgi-bin/stable_token`；`kernel/accessToken.go:282` —— 仅当 `ForceRefresh` 为真才在请求体下发 `force_refresh=true`。即各进程取到的是同一个仍然有效的 token，互不顶掉。

### 7.2 进程内竞争 → 评估后建议不额外处理

`GetToken`（`kernel/accessToken.go:99`）**无锁、无单飞**，`cache.Has` → `cache.Get` → `requestToken` → `SetToken` 为分离的非原子序列。缓存未命中时，多 goroutine 会并发请求 token。

两种解法：
- **(a) 注入 `GetCustomToken` 钩子**（`accessToken.go:43`，`:103` 处官方注释「如果客户有中控的场景，可以由客户自己提供token的方法」），内部用 `util.LocalCache.Fetch`（`util/cache.go:92`，持写锁）实现单飞 + 缓存。
  - **硬约束**：返回的 `object.HashMap` 必须满足 `token["expires_in"]` 为 **float64**、`token["access_token"]` 为 **string**，否则 `getFormatToken`（`accessToken.go:166-171`）的无保护类型断言会 panic。
- **(b) 不处理**。

**建议 (b)，理由**：7.1 的 stable_token 已经消除了并发取 token 的**有害后果**（旧 token 被顶掉），剩下的只是少量重复的 token 请求；而 `LocalCache.Fetch` 持的是**写锁**，会把所有 token 获取串行化，在并发下反而成为瓶颈。符合「简化」诉求。（需确认，第八节第 4 项）

### 7.3 必须替换默认 Cache —— 本轮最重要的发现

PowerWeChat 未配置 `UserConfig.Cache` 时，`NewInteractsWithCache`（`kernel/interactWithCache.go:29-39`）会调 `createDefaultCache()`（`:59`）创建 `cache.NewMemCache("ac.go.power", time.Duration(1500), "")`。该实现（`PowerLibs/cache/memory.go`）有四处硬伤：

1. **每次 `Set` 都写磁盘**：`memory.go:94-105` 在 `cache.Cache.Set` 之后紧跟 `SaveFile(cache.cacheFile)`。token 刷新即落盘。
2. **缓存文件路径固定且会被截断**：`createCacheFile`（`memory.go:57-82`）在 directory 为空时取 `os.UserHomeDir()`，落在 `~/.ArtisanCloud/cache`。**同机多进程写同一个文件**，而每个进程启动时的 `os.Create(cachePath)` 会**截断**它。（`LoadFile` 已被注释掉，`memory.go:47`，所以并不真正共享，纯属无意义的互相破坏。）
3. **HOME 不可写时会 panic**：`createCacheFile` 用 `os.Mkdir`（非 `MkdirAll`）；失败时 `NewMemCache` **返回 nil**（`memory.go:35`）→ `createDefaultCache` 把 nil 赋给 `Cache` → `GetCache()` 返回 nil 接口 → `accessToken.go:110` 的 `cache.Has(cacheKey)` **nil 指针 panic**。容器只读根文件系统、非 root 用户无 HOME 等场景会直接命中。
4. **`Add`/`AddNX`/`Remember` 是空实现**（`memory.go:114-124`），不能用于任何原子操作；且 `ACCache` 是包级全局单例（`memory.go:23,52`）。

**另注**：构造 `NewOfficialAccount` 时 `NewAccessToken` 必然执行，`NewInteractsWithCache` 必然执行 —— 所以上述风险在**SDK 构造阶段**就触发，不是延迟到首次发送。

**结论：必须注入自定义 `UserConfig.Cache`**（`officialAccount/application.go:106`）。注入后 `NewInteractsWithCache` 走 `cacheClient != nil` 分支，`createDefaultCache` 完全不执行，上述四处硬伤一次性全部规避。

实现成本已核实为很低：
- PowerWeChat src 全量 grep 确认 `Add`/`AddNX`/`Remember` **无任何调用点**，Cache 仅以 `Has`/`Get`/`Set` 被 `accessToken.go` 和 `basicService/jssdk/client.go` 使用 → 只需正确实现三个方法，其余空实现即可。
- 底层可直接复用 `util.LocalCache`（`util/cache.go:36`）。
- **硬约束**：`Get` 必须返回 `map[string]interface{}`，因为 `accessToken.go:113` 做 `value.(map[string]interface{})` 无保护断言。默认 MemCache 之所以不 panic，正是因为它在 `Set` 时 `json.Marshal`、在 `Get` 时 `json.Unmarshal` 成 `interface{}`（`memory.go:84-105`）。**自定义实现必须保持同样的 JSON 往返语义，不能直接存取结构体指针**，否则必 panic。

> 证据等级说明：以上为**代码级确认**（逐行读取 PowerLibs/PowerWeChat 源码），**非实测**。本机 `~/.ArtisanCloud/` 目录不存在，说明 msg_gateway 未在本机实际运行过（或运行环境 HOME 不同），因此第 2、3 条是代码路径推导出的风险，尚无线上现象佐证。

## 三、实施中发现并修正的两处问题

这两处都是对话2 方案在落码时才暴露的缺陷，已修正并各有用例锁定。

### 3.1 SDK 初始化失败会被重试 3 次，白等 3 秒

对话2 方案把 `GetWxSdk` 放在 `reTryWx` 的闭包内。但凭证缺失是**配置类错误**，重试必然同样失败，而 `isWxErrRetry` 对非 `wxRespErr` 一律判为可重试 → 凭证没配时每次调用要空等 `1s + 2s`。
msg_gateway 用「错误信息含『初始化SDK』就直接返回」绕过（`sdk/sdk.go:68-70`），是字符串匹配，脆弱。
**修正**：把 `GetWxSdk` 提到重试循环之外（`GetWxOpenIdList`/`GetWxUserInfos`/`GetWxTemplates`/`SendWxTemplateMsg` 四处），SDK 构造不是网络调用，本就不该进重试。顺带让翻页与分批循环只构造一次 SDK。

### 3.2 抑制锁在发送失败后不释放，会把告警吞掉

内容去重用 `LocalCache.TryLock` 在**发送前**加锁。若随后发送失败，锁仍持有 5 分钟，调用方在窗口内重试会被静默抑制并返回 `nil` —— 等于丢告警，与「宁可重复，不可丢失」直接冲突。
**修正**：发送失败时 `UnLock` 释放抑制锁；`SendWxMsg` 的 panic 恢复回调中也释放（panic 路径同样算失败）。
为此把 `SendWxMsg` 拆成外层（panic 恢复 + 抑制 + 释放）与内层 `sendWxMsg`（实际发送），以保证 defer 的 LIFO 顺序下「先由恢复回调写 err、再据 err 决定释放」。
用例 `TestSendWxMsgReleaseRepeatLockOnFail` 锁定该行为：凭证缺失时连续两次发送必须都返回 error，第二次不得被抑制成 `nil`。

## 四、关键实现点与依据

### 4.1 自定义 Cache（对话2 判定的必须项）

`newWxCache` 实现 `kernel.CacheInterface`，底层复用 `LocalCache[[]byte]`（`util/cache.go:36`），并以 `var _ kernel.CacheInterface = (*wxCache)(nil)` 做编译期接口校验。

- **Get 返回 `map[string]interface{}`**：`kernel/accessToken.go:113` 对缓存值做无保护断言 `value.(map[string]interface{})`，默认实现不 panic 靠的是 `Set` 时 `json.Marshal`、`Get` 时 `json.Unmarshal`（`PowerLibs/cache/memory.go:84-105`）。本实现用 `JsonStruct2Data`/`JsonData2Struct`（`util/json.go`）保持同样的 JSON 往返语义。
- **未命中返回 `defaultValue` 且 err 为 nil**：`GetToken`（`accessToken.go:110-116`）靠 `err == nil && value != nil` 决定是否用缓存，未命中必须让它回落到 `requestToken`。
- **TTL 削去 5 分钟余量**：PowerWeChat 写 token 时 TTL 等于微信返回的 `expires_in`，没有余量（`accessToken.go:148-153`），临界点会用到刚失效的凭证。削余量用一次多余的取 token 换掉一次必然失败的业务请求。同时对 `expires <= 0` 兜底，避免被 go-cache 的「0 表示使用默认过期时间」缩短。
- **`Add`/`AddNX`/`Remember` 留空**：PowerWeChat 全量 grep 无调用点，实现它们等于写死代码。用例 `TestWxCacheNoOpMethods` 固化该语义，防止将来误以为可用于原子操作。

### 4.2 access_token 竞争

`StableTokenMode = true` + `ForceRefresh = false`（依据 `officialAccount/auth/accessToken.go:26-33`、`kernel/accessToken.go:282`）。进程内单飞按对话2 决策不做。

### 4.3 错误三分层与重试

`wxRespErr` 把 `errcode != 0` 转成 error（PowerWeChat 不会转，见 `kernel/baseClient.go:505-571`），`isWxErrRetry` 用 `errors.As` 分类：

- 传输层（Go err 非空，含 HTTP 非 200，`baseClient.go:487`）→ 重试
- 业务层 `errcode == -1`（系统繁忙）→ 重试
- 业务层其他 errcode（含 40001/40014/42001）→ 不重试。凭证类已由 PowerWeChat 中间件刷 token 并重放一次（`baseClient.go:537-568`）；未知码默认不重试
- 重试 3 次，间隔 `SleepWare` 的 `{1s, 2s}`（对齐 `util/http.go:25`，带 ±10% 抖动），每次尝试前 `CtxDone` 短路

**errcode 白名单当前只有 `-1`**。这是保守起点：对话2 已记录「具体可重试码集合须对照微信官方《全局返回码说明》核定」，本轮无法访问该文档，故只纳入含义最明确的系统繁忙码，其余一律不重试。扩充该白名单只需改 `isWxErrRetry` 一处。

### 4.4 超时预算

`sendWxMsg` 在 ctx 没有 deadline 时补 `WxTimeoutDefault`（10s）。依据：取 token 的 HTTP client 没有客户端级超时（`kernel/accessToken.go:67-74` 未设 `ClientConfig.Timeout`），ctx 是同步调用方唯一兜底，而 `GenCtx()`（`util/ctx.go:26`）基于 `Background` 不带 deadline。发送侧另有 `cfg.Http.Timeout = 10s`（`baseClient.go:57`）。

### 4.5 消息体

模板唯一占位符 `{{data.DATA}}`，请求体形如 `{"data": {"data": {"value": "<多行字符串>"}}}`（外层 `data` 是请求字段，内层是占位符名）。值为：

```
sn: {GetServerName()}
ip: {GetIP()}
log: {Int2Str(GetLogId(ctx))，为0时留空}
{正文}
```

字段名复用 `ServerNameKey`/`IpKey`（`util/log.go:21-22`），日志行另定 `wxLogKey = "log"` —— 按模板约定是 `log`，与 `LogIdKey`（`"logid"`）不同，用例 `TestWxConstants` 断言两者不相等以防误用。

正文按 rune 截断到 `WxTextLenMax = 1000` 并加 `...(已截断)` 标记。**该阈值不是微信的限制，而是我们的保守保护**：单占位符结构下长度压力集中，而微信对占位符取值的上限仍未确认（见第六节）。

### 4.6 最早关注者

`User.List` 分页（游标为空或未推进即退出，`wxUserPageMax = 100` 轮仅防死循环）→ `Distinct` 去重 → 恰好 1 人直接采用（省一次调用）→ 多人时 `User.BatchGet` 批量取 `SubscribeTime`，取最小，同秒关注时以 openid 字典序 tie-break 保证结果确定。多关注者时打 Warn 提示配置 `wx_open_id`。

不依赖 `User.List` 的返回顺序：该顺序是否等于关注顺序没有任何依据。

### 4.7 元数据缓存

`wxOpenIdCache` 与 `wxTemplateIdCache` 是**两个独立实例**：`LocalCache.Fetch` 持写锁，分开后接收人与模板的解析互不阻塞。空结果一律判为 error，而 `Fetch` 在 get 报错时不写缓存（`util/cache.go:85-88`），因此「空值不入缓存」自动成立 —— 对话2 提到的 msg_gateway「1h + 5min 双 TTL」补偿（`template_message.go:15-29`）因此不再需要。

### 4.8 panic 隔断

`initWxSdk` 与 `SendWxMsg` 都用 `util.Defer`（`util/os.go:97`）把 panic 转成 error。理由：PowerWeChat/PowerLibs 中存在多处无保护类型断言（已定位 `accessToken.go:113`、`:166-171`，`zap/log.go:69`、`:152-153`），微信是旁路能力，其内部 panic 不应击穿调用方主业务。

## 一、StableTokenMode 与 ForceRefresh 的作用

### 先说背景

调微信任何接口都要带 `access_token`。它是 **AppID 级的全局凭证**——同一个公众号下所有服务共用一个，不是每个进程一份。微信提供两个获取它的接口：

- `cgi-bin/token`：老接口
- `cgi-bin/stable_token`：稳定版接口

### 两个参数分别决定什么（代码级确认）

**`StableTokenMode` 决定用哪个接口。**
依据 `officialAccount/auth/accessToken.go:26-33`：为 `true` 时把取凭证的端点换成 `cgi-bin/stable_token`（同时依据 `kernel/accessToken.go:244` 把请求方法改为 POST）；为 `false`（默认）时用 `cgi-bin/token`。

**`ForceRefresh` 决定是否要求微信换一个新凭证，且只在稳定版接口下才有意义。**
依据 `kernel/accessToken.go:282-283`：只有 `StableTokenMode && ForceRefresh` 同时为真时，才会在请求体里加上 `force_refresh = true`；否则这个字段根本不发。

### 通俗类比

把 access_token 想成**公司前台的一把通用钥匙**：

- **老接口 `cgi-bin/token` 像「重新配一把钥匙」**：每次调用都生成新钥匙，旧钥匙作废。如果 A 服务和 B 服务都去配，B 配完之后 A 手里那把就不好使了——这就是「互相顶掉」。
- **稳定版接口 + `ForceRefresh=false` 像「问前台现在的钥匙是哪把」**：只告诉你当前有效的那把，不重新配。A 和 B 都来问，拿到同一把，谁都不受影响。
- **稳定版接口 + `ForceRefresh=true` 像「让前台重新配一把」**：旧的作废，行为退回老接口。

### 所以我们配 `StableTokenMode=true, ForceRefresh=false` 的含义

「用稳定版接口，而且只问当前凭证、不强制换新」。

这是必须的，因为 msg_gateway 废弃后格局变了：以前只有网关这一个进程持有凭证，天然不会冲突；现在 `go_common` 被所有项目引用，**每个配置了微信的进程都会独立取凭证**，而 PowerWeChat 的凭证缓存是进程内内存（`kernel/interactWithCache.go:61`），进程之间互不可见。

两种配错的后果：

| 配置 | 后果 |
| --- | --- |
| `StableTokenMode=false`（默认） | 多进程互相顶掉，表现为随机出现 `40001 invalid credential`。SDK 的中间件会自动刷凭证重放一次（`baseClient.go:537-568`），所以能自愈，但每次自愈都要先失败一次请求 |
| `StableTokenMode=true, ForceRefresh=true` | 虽然走了稳定版接口，但每次都强制换新凭证，等于白用——照样互相顶掉 |

### 必须说清的边界

上面「老接口会使旧凭证失效」「稳定版不强制刷新时返回当前有效凭证」这两条是**微信服务端的行为**，从 PowerWeChat 代码里读不出来。代码能证实的只有「选了哪个端点、是否下发 `force_refresh`」。服务端语义需对照微信官方文档《获取稳定版接口调用凭据》确认——这条已记入第五节「待确认」。

本轮新增用例 `TestWxSdkStableTokenMode` 锁定代码侧的三件事：`StableTokenMode` 为真、`ForceRefresh` 为假、取凭证端点含 `stable_token`。

### 完全移除

| 移除项 | 原作用 |
| --- | --- |
| `reTryWx` | 泛型重试包装 |
| `isWxErrRetry` + `wxErrCodeBusy` + `wxSleeps` | 错误分类与重试间隔 |
| `WxTryDefault` | 重试次数 |
| `wxOpenIdCache` + `wxTemplateIdCache` + `WxMetaTimeout` | 接收人与模板的元数据缓存 |
| `wxRepeatCache` + `WxRepeatTimeout` | 相同正文的去重抑制 |
| `wxRespErr` 类型 | 为重试分类服务的错误类型，改用普通 error |
| `sendWxMsg` 内层函数 | 拆成内外两层只为了配合抑制锁的 defer 顺序，抑制去掉后两层合一 |

连带消失的复杂度：

- **错误处理从「包装成可被 `errors.As` 识别的类型」退回普通 error**。原来之所以需要一个类型，是因为重试要按 errcode 分类；不重试了，就只需要一句人能读懂的错误文本。
- **`SendWxMsg` 从两层变一层**。原来外层管 panic 恢复 + 抑制锁获取/释放、内层管发送，是为了保证 defer LIFO 下「先由恢复回调写 err、再据 err 释放锁」。没有锁要释放，这个结构就没必要了。
- **元数据每次都重新查**。代价是每条消息多 1~2 次微信接口调用；收益是没有「缓存了空值怎么办」「什么时候失效」「多个缓存实例会不会互相阻塞」这一串问题。

### 中途自我纠正的一处

第一版简化我写了一个 `genWxErr(ctx, name, errCode, errMsg, err)` 统一处理四个调用点，结果调用点变成 `genWxErr(ctx, name, 0, "", errors.Errorf("响应为空: %+v", err))`——传两个占位参数、再把 err 包一层只为了塞进同一个函数。这正是对话4 说的「绕」。
改成：传输层错误在调用点扁平展开（项目既有写法），只把四处完全相同、语义独立的 errcode 校验抽成 `checkWxErrCode(ctx, name, errCode, errMsg)`，签名里没有占位参数。

### 没有去掉的两项，以及为什么

这两项名字里带「缓存」或看着像「保护逻辑」，但去掉会埋坑，所以保留并说明：

**1. `wxCache`（注入给 SDK 的 access_token 存储）**
这不是业务缓存，而是 SDK 取凭证必须用到的存储。不注入它，SDK 就落到默认实现，而默认实现（`PowerLibs/cache/memory.go`）有三个已**实测确认**的问题：每次写入都往 `~/.ArtisanCloud/cache` 落盘、同机多进程互相截断该文件、HOME 不可写时 `NewMemCache` 返回 nil 导致取凭证时 panic。
去掉它不是简化，是把一个确定的故障放回去。
本轮已把它从 ~45 行压到最朴素的 JSON 往返：删掉了「TTL 削 5 分钟余量」这个优化（它是「绕」的来源之一），也删掉了 `expires <= 0` 的兜底——核对 `kernel/accessToken.go` 的 `SetToken` 确认它会先把 `ExpiresIn <= 0` 兜成 7200 再传进来，所以那个分支是死代码。

**2. errcode 显式校验（`checkWxErrCode`）**
这不是重试逻辑。SDK 在 errcode≠0 时 Go error 仍为 nil（v3.4.45 已重新核对），去掉校验就会回到 msg_gateway 的静默失败缺陷：「模板ID错 / 用户未关注 / 超配额」全都表现为「消息没到但一切正常」。
这是对话1 第二节记录的现状缺陷之一，不能在简化的名义下重新引入。

另外 `cutWxText`（正文截断）与 ctx 超时兜底都不属于缓存或重试，各 4~8 行、无状态、读一遍就懂，一并保留。

## 三、本轮发现的一个风格问题：注释量本身就是复杂度

统计项目里所有非测试源文件的声明级注释（`grep -cE '^//'`）：

```
util/log.go: 3      （全是 // Deprecated: 标记）
util/math.go: 2
util/struct.go: 2
其余 20 个文件: 0
util/wechat.go: 37  ← 我写的
```

函数内注释也同样稀疏：`util/cache.go` 与 `util/sync.go` 是 0，`util/http.go` 是 6。

也就是说项目风格是**近乎不写注释**，而我那个文件一个人贡献的注释比全项目其余文件加起来还多 4 倍。370 行代码被摊成 582 行，读起来就是「绕」——这部分「复杂」不在逻辑里，在我的注释里。

这一点也有用户改动为证：提交 `10b5609` 把我 `GetWxSdk` 的三行文档注释整段删掉，并把 `Defer` 回调参数名从 `panicValue` 改回 `panic`（核对 `util/config.go:65`、`util/http.go:211`，`panic` 确实是项目既有写法，我当时为了不遮蔽内建函数自作主张改了名）。

本轮处理：
- 声明级注释 37 → 6，与项目其他文件持平；
- 参数名改回 `panic`，与项目一致；
- 只在 6 处留短注释——都是「删掉这行代码会静默出错」的地方：`wxCache` 为何存在、`Get` 必须返回 map、errcode 必须显式校验、ctx 是唯一超时兜底、上下文取不到为何留空、模板为何取第一个；
- 详细依据全部留在本文档。流程文档本就规定「关键结论/方案取舍/验证结果统一记录至 `answer.md`」，这些内容的归处是这里，不是源码。

## 五、待确认（本轮增量与存量）

1. **微信服务端对两个取凭证接口的语义**（新增）：老接口刷新是否使旧凭证失效、稳定版接口在 `force_refresh=false` 时是否返回当前有效凭证。代码只能证实端点选择与参数下发，服务端契约需对照微信官方文档《获取稳定版接口调用凭据》。这是 `StableTokenMode=true` 能解决竞争的前提。
2. **`cgi-bin/stable_token` 自身的调用频率限制**（存量）：去掉元数据缓存后每条消息的接口调用次数上升，若 stable_token 有较紧的频控需要重新评估。
