# 执行流程

> 你是一位拥有跨学科背景的顶尖资深专家，请以深厚的专业洞察力和严谨的大师视角进行回复
> 流程冲突时以「任务 Prompt」为准
> 关键结论/方案取舍/验证结果统一记录至`260909-224806-answer.md`(`prompt.md`路径相同)

## 步骤

- 背景调研
    - 研读prompt中提及的文档/代码/配置
    - 对齐背景，梳理核心逻辑/组件依赖/改动点
- 需求分析与方案
    - 提取核心目标/交付物/范围边界/关键约束
    - 制定方案：最小改动/复用优先/任务拆解；说明模块职责/输入输出/关键逻辑/异常处理
    - 评估对现有链路/性能/兼容性/下游的副作用
    - 写入`answer.md`：依据来源/方案取舍/实施步骤/验证说明
- 实施
    - 按方案执行，命名/注释/文案与项目风格一致
    - 中文注释与日志，处理边界与异常分支
    - 同步更新类型定义/关联配置/文档
    - 复杂任务使用主agent调度子agent的方式实施
- 验证与交付
    - 执行测试/逻辑校验/数据校验/文档校对
    - 重读`prompt.md`，检查与交付结果是否一致
    - 核心产出同步至`answer.md`
    - 清理临时文件/调试代码/冗余产物，但无须提交变更

## 约束

- 依据：结论只能来自文档/代码/表结构/日志/SQL等明确来源；严厉禁止猜测业务逻辑/捏造接口字段，不能断言的内容都询问用户
- 引用：关键事实引用到具体章节/字段名/代码路径或枚举值，禁止笼统援引
- 信息不足：区分「已确认/待确认/不可推断」并标注，不得脑补
- 历史资料：历史Prompt/answer/旧方案仅供参考，必须与代码交叉核对后才能使用
- 冲突：资料冲突时列出冲突点与采用依据，不得默默取一方
- 风格：命名/注释语言/代码组织与项目既有风格一致，优先复用现有实现

## 具体任务

+ 阅读本代码仓库的全部代码，我对代码进行过大面积的重构
+ 你需要review的问题，包括但不限于
+ 每个函数的逻辑是否正确
    + 业务逻辑是否正确
    + 依赖库的调用是否正确
    + 并发与锁处理是否正确，是否会有死锁或者重入问题
+ 每个函数处理边界case是否可靠
+ 成对的函数是否缺少
    + 例如有个函数是AtoB，如果逻辑可逆，是否缺少BtoA的函数
+ 成对的函数处理逻辑是否对称
    + 函数AtoB，与函数BtoA的入参出参，处理逻辑，是否对称可逆
+ 每个函数的代码风格与变量命名风格是否一致统一
    + 对于某个变量，是采用大写还是小写，是使用指针还是struct
+ 修复代码
    + 不能破坏性改动，**需要沿用现有代码风格与结构**
    + 历史的commit代码可能是有其作用，但是我为了代码仓库的简洁与易维护性进行了精简
    + 阅读历史代码能指导需要注意什么，但不要无脑把历史代码恢复回来
    + 代码不要过度细化封装
    + 不要加一堆的注释，我写的代码我能不知道是什么回事吗
