### 1.1 断点在哪（逐行核对，非推断）

| 位置 | 代码 | 写/读的是哪个容器 |
| --- | --- | --- |
| `util/gin.go:140` | `c.Set(ClaimsKey, claims)` | **gin.Context.Keys**（map） |
| `util/gin.go:65` | `c.Set(LogIdKey, logId)`（`setGinLogId`） | **gin.Context.Keys** |
| `util/gin.go:147` | `ctx := c.Request.Context()`（`NewGinGet`） | **http.Request 的 ctx** |
| `util/gin.go:161` | `ctx := c.Request.Context()`（`NewGinPost`） | **http.Request 的 ctx** |

两个容器之间的可见性是**单向**的，依据 `gin@v1.12.0/context.go`：

```go
func (c *Context) Value(key any) any {
	...
	if keyAsString, ok := key.(string); ok {
		if val, exists := c.Get(keyAsString); exists { return val }   // 先查 Keys
	}
	if !c.hasRequestContext() { return nil }
	return c.Request.Context().Value(key)                             // 再回落到请求ctx
}
func (c *Context) hasRequestContext() bool {
	hasFallback := c.engine != nil && c.engine.ContextWithFallback    // 默认 false
	...
}
```

即：`gin.Context` 有条件地能看见请求ctx（还得 `ContextWithFallback` 打开），而**请求ctx 永远看不见 `gin.Context.Keys`**。`ValidateGin` 写在 Keys 里，`NewGinGet`/`NewGinPost` 从请求ctx 读——方向正好逆着，于是：

- service 侧 `GetClaims[T](ctx)`（`util/gin.go:51` → `GetCtxValue` 断言失败被吞，`util/ctx.go:9`）**恒为 nil**；
- service 侧 `GetLogId(ctx)`（`util/log.go:121`）**恒为 0**，连 `NewGinPost` 自己那行 `logrus.WithContext(ctx)...Info(name)`（`util/gin.go:169`）打出来的 logId 都是 0——`LogrusHook.getLogId` 读的就是 `entry.Context`（`util/log.go:73`）。

所以**claims 与 logId 是同一个断点的两个症状**：`ValidateGin` 往 gin.Context 上写的东西，一样都过不去。

## 二、方案取舍

断点只有两种补法：**把值送到请求ctx 去**，或**把 service 拿到的 ctx 换成 gin.Context**。

| 方案 | 改动 | 结论 |
| --- | --- | --- |
| **A（采用）** 在 `ValidateGin`/`setGinLogId` 里写透到 `c.Request` | `util/gin.go` **+2 行** | 两侧都有值，`gin.Context` 侧一行不动（下游 `GetClaims(c)` 的写法全部保留）；service 拿到的仍是真正的请求ctx，取消/超时信号照旧 |
| B 把 `NewGinGet`/`NewGinPost` 的 `ctx := c.Request.Context()` 改成 `ctx := c` | `util/gin.go` 改 2 行 | **否决**，见下 |
| C 不改库，让下游 handler 自己包一层把 claims 塞进请求ctx | 库 0 行，下游 N 处 | **否决**：`NewGinGet`/`NewGinPost` 存在的意义就是免掉这层样板，要下游每个路由再包一次等于把构造器废掉 |

**B 为什么否决**（两条都是代码事实，不是偏好）：

1. **service 会丢掉取消信号**。`gin.Context.Done()/Deadline()/Err()` 在 `hasRequestContext()` 为 false 时一律返回零值（`gin@v1.12.0/context.go`），而 `hasRequestContext` 要求 `engine.ContextWithFallback`；jotcash 用的是 `gin.Default()`（`jotcash/handler/handler.go:29`），这个开关是关的。于是客户端断开、请求超时，service 里的 `CtxDone(ctx)`（`util/ctx.go:47`）、gorm 的 `WithContext(ctx)`、`util.Transaction` 的取消语义**全部失效**。B 等于拿"值取不到"换"取消信号取不到"。
2. **`gin.Context` 出自 `sync.Pool`**，handler 返回后对象被回收复用。service 只要把 ctx 存进结构体、丢进 `SingleGoPool`（`util/sync.go`）或任何异步路径，读到的就是下一个请求的数据。A 交出去的是 `*http.Request` 的 ctx，值不可变，没这个风险。

**A 的代价**：每次 `ValidateGin` 多 2 次 `http.Request` 浅拷贝（`WithContext` 是 `r2 := new(Request); *r2 = *r`，约 200B，Body/Header 指针照抄，`ShouldBindJSON` 读 Body 不受影响）。鉴权本身有一次 JWT 验签（RSA/HMAC），这点拷贝可忽略。

**为什么 logId 也一起补**：`setGinLogId` 与 `c.Set(ClaimsKey,...)` 是同一个函数里同一种写法的同一个断点，只补 claims 会留下"claims 通了、logId 还是 0"的半截状态；且上一轮（`260914-224155`）刚刚为跨服务 logId 贯通加了 `TestValidateGinLogIdFromClaims`（`util/gin_test.go:517`），补了 claims 却让 service 侧日志继续打 `logid:0`，那条链路等于只通到 handler 门口。代价是 1 行。

func setGinLogId(c *gin.Context, logId int64) {

几处刻意的取舍：

- **`c.Set` 一行不删**。下游 `GetClaims[*model.Claims](c)` 的写法遍地都是（`util/gin.go:47` 的 `Ping`、`jotcash/handler/ping.go:15`、`jotcash/handler/db.go:33/47`、`jotcash/handler/expense.go:16`），删掉就是另一个方向的断裂。两侧同时写，取到的是**同一个 claims 实例**（第四节有断言）。
- **claims 复用 `SetClaims`（`util/gin.go:54`）而不是直接 `SetCtxValue`**：`SetClaims` 带 `IsNil` 防护（`util/transform.go:331`，`util/gin_test.go:114-128` 锁着"nil/空指针不得污染ctx"这条），复用它就不必在中间件里再写一遍判空。
- **logId 用 `SetCtxValue(ctx, LogIdKey, logId)` 而不是 `SetLogId`**：`SetLogId`（`util/log.go:124`）是"没有才生成"，塞不进指定值；`ReSetLogId` 已标 Deprecated。这个写法与 `CopyCtx`（`util/ctx.go:34`）里的 `SetCtxValue(ctx, LogIdKey, GetLogId(old))` 完全一致。
- **写透点放在 `setGinLogId` 内部**，不是在 `ValidateGin` 里各补一次：`setGinLogId` 在 `ValidateGin` 里被调用两次（入口 `util/gin.go:79`、采信 claims 里的 logId 后 `util/gin.go:113`），放进函数里两次都覆盖，且鉴权失败被 `c.Abort()` 的路径上请求ctx 里也有 logId。
- **不加 `c.Request == nil` 防护**：`ValidateGin` 紧接着就是 `c.Request.Header.Get(...)`（`util/gin.go:82`）、`c.Request.RequestURI`（`util/gin.go:131`），`GinLog`（`util/log.go:109`）同样裸取，本来就没有"Request 可以为 nil"这条前提，加了反而与全文风格不一致。
- **生产代码不写注释**：`util/gin.go` 原本 0 条注释，与 `util/sync.go`、`util/cache.go` 一致，本轮不破例；不变量由下面两个用例守住。

### 6.1 前提：回落是**单向且默认关闭**的（已实测）

写了个临时用例实跑（跑完即删），只往请求ctx 写值、不写 Keys，两种开关下分别读：

```
fallback=false: GetClaims(c)=<nil>              GetLogId(c)=0    | GetClaims(req)={"ip":"1.1.1.1"} GetLogId(req)=123
fallback=true : GetClaims(c)={"ip":"1.1.1.1"}   GetLogId(c)=123  | GetClaims(req)={"ip":"1.1.1.1"} GetLogId(req)=123
```

`gin.New()`/`gin.Default()` 的 `ContextWithFallback` 默认是 `false`，全仓库+4 个依赖项目没有任何一处打开它（`grep -rn ContextWithFallback` 只命中 survive_monitor 的 vendor 目录和本轮新写的注释）。所以在**当前配置下**，`c.Set` 这两行是 gin.Context 那一侧的**唯一**数据来源——本轮加的两行写透只能供请求ctx 那一侧用，反向补不上。

### 6.4 `c.Header(LogIdKey, ...)`：它压根不在"两者不通"这个问题域里

这行写的是 **HTTP 响应头**，不是任何进程内 ctx，和 `NewGinPost` 的链路没有关系，谈不上被请求ctx 取代。

**仓库内没有代码读它**（已核对）：go_common 的 http 客户端只设请求头（`util/http.go:156` `client.SetHeader`），没读过响应头；jotcash/mmm/msg_gateway/survive_monitor 里 grep 不到读 `logid` 响应头的代码；jotcash 的前端资源不在仓库里（`jotcash/static/` 下只有 `static.go` 的 `//go:embed`），无法核对。

所以它的消费方只能是**人**——从浏览器 DevTools/curl 的响应头拿到 logId，去服务端日志里搜同一个 id。**这一点我没有代码依据，标记为待确认**（第五节第 3 条）。但删除的收益是 1 行代码，代价是排查线上问题时对不上号，不对称，**不建议删**。

实测（删掉该行）：`TestSetGinLogId`、`TestValidateGinLogIdFromClaims`、`TestValidateGinCtxBothSides` 三处响应头断言全红。

### 6.5 什么条件下这三行才真的能删

两条路，**都与"最小改动"相反，本轮不做**：

1. **下游每个 engine 打开 `ContextWithFallback`**（6.1 实测过，打开后 `GetClaims(c)`/`GetLogId(c)` 能从请求ctx 取到，`c.Set` 两行就冗余了）。但 go_common 不创建 engine，得每个下游项目自己设（`jotcash/handler/handler.go:29` 是 `gin.Default()`）；而且这个开关同时会把 `Done()/Deadline()/Err()` 接到请求ctx 上，行为变化不止"取值"这一项，需要单独评估。
2. **把所有"传 `c` 当 ctx"的 handler 改成传 `c.Request.Context()`**（6.2 那 5 个 + 其他项目）。跨仓库改动，且 `c` 当 ctx 用是 gin 的常规写法，改完还得防止有人写回去。

### 6.6 顺带澄清一个可能的误读

本轮之后 claims/logId 确实"写了两份"，但这**不是冗余**：Keys 与请求ctx 是 gin 里并存的两套容器，各有各的读者（6.2/6.3），回落又只有一个方向（6.1）。两份写的是**同一个 claims 指针**（`TestValidateGinCtxBothSides` 断言 `GetClaims(c) == GetClaims(c.Request.Context()) == 传入实例`），logId 是同一时刻同一来源的 int64，不存在两边不一致的风险。

## 七、第二轮：全链路改用 `c.Request.Context()`，两行 `c.Set` 删除

### 7.1 为什么必须走这条路（你给的理由，已逐条核到源码）

`*gin.Context` **不是一个能活过本次请求的对象**：

```go
// gin@v1.12.0/gin.go ServeHTTP
c := engine.pool.Get().(*Context)
c.writermem.reset(w)
c.Request = req
c.reset()
engine.handleHTTPRequest(c)
engine.pool.Put(c)          // 请求一结束就还池
```

```go
// gin@v1.12.0/context.go reset
c.Keys = nil                // 下一个请求进来时，上一位的 claims/logId 直接被抹掉
```

而把它当 ctx 交给 `database/sql`，ctx 会被**请求结束之后仍在跑的协程**读：

```go
// go1.27 src/database/sql/sql.go:3015
func (rs *Rows) awaitDone(ctx, txctx, closectx context.Context) {
	select {
	case <-ctx.Done():                 // Rows 关掉之前，这个协程一直在读 ctx
		err := ctx.Err()
	...
	rs.close(ctx.Err())
}
// :2214
func (tx *Tx) awaitDone() { <-tx.ctx.Done(); ... tx.rollback(discardConnection) }
```

两边叠起来的后果（按当前 `ContextWithFallback=false` 的配置）：`Context.Done()`/`Err()` 内部要读 `c.engine` 与 `c.Request`（`hasRequestContext()`），而此刻 `c` 可能已经被下一个请求 `c.Request = req; c.reset()` 改写——**这是一个跨请求的数据竞争**；若哪天为了取值把 `ContextWithFallback` 打开，语义会更糟：老查询的 `awaitDone` 盯上的是**新请求**的取消信号，新请求一结束就去 rollback/close 老事务的连接。

所以正确的做法不是"让 `gin.Context` 也能取到值"，而是**任何地方都不把 `*gin.Context` 当 `context.Context` 交出去**。`c.Request.Context()` 是 `*http.Request` 上的不可变 ctx，值不会被别人改写，取消信号也是本次请求自己的。

### 7.2 go_common 的改动（3 个文件，生产代码净 -1 行）

| 位置 | 改动 |
| --- | --- |
| `util/gin.go:47` `Ping` | `ctx := c.Request.Context()`，日志与 `GetClaims` 都用它 |
| `util/gin.go:61` `setGinLogId` | **删** `c.Set(LogIdKey, logId)`；只写请求ctx + 响应头 |
| `util/gin.go:79` `ValidateGin` 入口 | `setGinLogId(c, GetLogId(c.Request.Context()))` |
| `util/gin.go:95` | `DeJwt(c.Request.Context(), ...)` |
| `util/gin.go:124` | `TryLockReqId(c.Request.Context(), ...)` |
| `util/gin.go:140` | **删** `c.Set(ClaimsKey, claims)`；只留写进请求ctx 那一行 |
| `util/log.go:104` `GinLog` | `c.Next()` **之后**取 `ctx := c.Request.Context()`，三条访问日志都用它 |

`GinLog` 里取 ctx 的时机是这次唯一有坑的地方：`ValidateGin` 是用 `c.Request = c.Request.WithContext(...)` 写值的，**`c.Next()` 之前取到的是没有 logId 的老 ctx**，访问日志会掉回 `logid:0`。`TestGinChainOnlyRequestCtx` 专门钉这一条（反证见 7.4）。

留下的 `c.Header(LogIdKey, ...)` 不动：它写的是响应头，不是进程内通路（6.4）。

### 7.3 测试改动

- 所有断言从 `GetClaims(c)`/`GetLogId(c)` 改成 `GetClaims(c.Request.Context())`/`GetLogId(c.Request.Context())`：`TestSetGinLogId`、`TestValidateGinPass`、`TestValidateGinCustomClaims`、`TestValidateGinLogIdFromClaims`。
- `TestValidateGinCtxBothSides` → 改写为 **`TestValidateGinNotInGinKeys`**（`util/gin_test.go:678`）：断言请求ctx 里有 claims/logId、响应头有 logId，而 **`len(c.Keys) == 0`**——把"不许再往池化对象里塞值"这条钉死。
- 新增 **`TestGinChainOnlyRequestCtx`**（`util/gin_test.go:725`）：在真实 `gin.Engine` 上把 `GinLog` → `ValidateGin` → `NewGinPost` 三段串起来跑一次，断言 service 拿到 claims、访问日志与业务日志共用 claims 带来的同一个 logId、全程 `c.Keys` 为空。

### 7.5 下游（jotcash）必须同步改的点——**升级依赖前不改就是 claims 恒 nil**

`c.Set(ClaimsKey, claims)` 删掉之后，`util.GetClaims[*model.Claims](c)` 这种写法一律返回 nil。jotcash 需要把手写 handler 的第一行改成 `ctx := c.Request.Context()`，然后把下面这些 `c` 全部换成 `ctx`：

| 文件 | 行 | 现状 |
| --- | --- | --- |
| `handler/ping.go` | 15、16 | `logrus.WithContext(c)`、`GetClaims(c)`、`db.CheckToken(c)` |
| `handler/expense.go` | 16、17、20、26、30、31 | `GetClaims(c)`、`config.GetConfig(c)`、`util.CloseIo(c, file)`、`service.InsertExpense(c, ...)` |

## 八、一句话结论

断点不在 claims，在**方向**：`ValidateGin` 把值写进 `gin.Context.Keys`，而 `gin.Context` 能回落到请求ctx（还得 `ContextWithFallback` 打开）、请求ctx 却永远回落不到 Keys（`gin@v1.12.0/context.go` 的 `Value`/`hasRequestContext`），所以 `NewGinGet`/`NewGinPost` 交给 service 的 `c.Request.Context()` 里 claims 恒 nil、logId 恒 0，jotcash 那 5 个 `NewGinPost` 路由连加密库都打不开。

修法取"把值写透到 `c.Request`"而不是"让 service 直接拿 `gin.Context`"：后者只改 2 行，但 `gin.Default()` 没开 `ContextWithFallback` 时 `Done()/Deadline()/Err()` 全是零值，等于用"取消信号丢了"换"值取到了"，何况 `gin.Context` 来自 `sync.Pool`、异步持有就是脏读。

第一轮落成 `util/gin.go` **+2 行**（claims 一行、logId 一行，后者同一个断点的另一半症状），两侧同时可读、同一实例，下游 `GetClaims(c)` 的老写法全部保留。

至于那三行是不是没用了：在"下游继续用 `c` 当 ctx"的前提下，**都还在用**。`gin.Default()` 默认不开 `ContextWithFallback`，回落只有"gin.Context → 请求ctx"这一个方向（6.1 实测），所以 `c.Set` 两行是 gin.Context 那一侧的唯一来源——jotcash 有 5 个路由（明细入库/POST Ping/导出/导入，加上本库的 `util.Ping`）根本不走 `NewGinPost`，而是**直接把 `c` 当 ctx 传给 service**（`jotcash/handler/expense.go:31` 等），删了就是把刚修好的 bug 换个方向再犯一次；`c.Set(LogIdKey,...)` 撤了则 `GinLog` 的访问日志与所有 `logrus.WithContext(c)` 的 logId 全变 0；`c.Header(LogIdKey,...)` 写的是响应头，压根不在"两者不通"这个问题域里（唯一存疑的是它的人工消费方，已列入待确认）。三行各删一次的实测结果都在 6.2/6.3/6.4。

第二轮按你的判断把前提本身拆了：`*gin.Context` 请求一结束就 `engine.pool.Put(c)`、下个请求 `c.reset()` 把 `Keys` 置 nil，而 `database/sql` 的 `(*Rows).awaitDone`/`(*Tx).awaitDone` 协程会在请求返回后继续读 ctx——把池化对象当 ctx 交出去，本身就是一个跨请求的数据竞争。所以不是"让 gin.Context 也能取到值"，而是**全链路只认 `c.Request.Context()`**：`Ping`、`GinLog`、`ValidateGin` 内部的 `DeJwt`/`TryLockReqId`/`GetLogId` 全部换掉，两行 `c.Set` 随之删除（`c.Header` 是响应头，留着）。生产代码净 -1 行，249 PASS，新增的 `TestValidateGinNotInGinKeys` 钉住"不许再往 Keys 里写"，`TestGinChainOnlyRequestCtx` 在真实 engine 上钉住"访问日志/业务日志共用同一个 logId"——后者同时防住 `GinLog` 里 ctx 取早了（提到 `c.Next()` 之前就掉回 `logid:0`）。

**下游必须同步改**：jotcash 的手写 handler 还在用 `GetClaims(c)`，清单在 7.5，升级依赖前不改就是 claims 恒 nil。
