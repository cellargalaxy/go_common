### 2.3 「回滚」的落点：为什么不能复用原 tx

这是本轮 todo 唯一有实质技术含量的地方，先把不可行的路径钉死：

**不能把 rollback handler 挂在同一个 `Transaction(fc)` 闭包里**。gorm 的实现（`finisher_api.go`）是：`fc` 一旦返回非 nil，defer 里立刻 `tx.Rollback()`；且 `Rollback` 之后 `tx.Statement.ConnPool` 上的 `*sql.Tx` 已终结，再拿它发语句必定 `sql: transaction has already been committed or rolled back`。所以**闭包内部无论怎么写，都不可能在"主体已回滚"的状态下用同一个 tx 补偿**。

**只能在 `Transaction` 返回之后另起一个事务**，即 `Exec` 现在这个 `if err != nil` 分支的位置。改动把 todo 放在这里，位置是对的。

### 2.4 回滚的四条约束（实施时逐条落地）

| # | 约束 | 不这么做的后果 |
| --- | --- | --- |
| R1 | 另起事务，不复用原 tx | 见 2.3，必然报 `transaction has already been committed or rolled back` |
| R2 | 回滚跑在**摘掉取消信号**的 ctx 上 | 主事务最常见的失败原因之一就是 ctx 超时/取消（上游 http 断开、`context.WithTimeout` 到点）。同一个 ctx 跑补偿，`database/sql` 在 `BeginTx` 就直接返回 `context canceled`——**越是需要补偿的场景，补偿越跑不起来** |
| R3 | 回滚自身的错误**不得顶掉**主事务的根因 | 调用方拿到的是"回滚失败"，真正的业务失败原因（唯一键冲突、字段超长……）当场丢失，线上无法定位 |
| R4 | 没有 rollback handler 时**不得空开事务** | 否则每次业务失败都多一次 BEGIN/COMMIT 往返。在 jotcash 的 SQLite 上尤其贵：连接串带 `_txlock=immediate`（`jotcash/db/db.go:52`），**BEGIN 当场就抢写锁**，等于给每一次失败都加一次全库写锁 |

R2 的 ctx 处理有两个候选，取舍如下：

| 方案 | 写法 | 结论 |
| --- | --- | --- |
| A | `util.CopyCtx(ctx)`（`util/ctx.go:31`） | 项目自有、语义对口（`util/ctx_test.go:118` 写着"副本不应随原ctx一起取消（这是该函数的核心用途）"），但它是 `GenCtx()` 起一棵新树，**只搬 `ignoreErr`/`logId`/`reqId` 三个值**，ctx 上其余的值（如下游塞的 claims）全部丢失 |
| **B（采用）** | `context.WithoutCancel(ctx)` | 标准库（go 1.21+，本仓库 `go 1.27`），**只摘取消与 deadline，值全量保留**。日志id、reqId、claims 一个不丢 |

B 是 A 的严格超集：A 能保住的三个值 B 也保住，A 丢掉的值 B 没丢，且不引入新的 helper。实测日志已验证 logId 串得起来（第四节）。

### 2.5 复核过但**未改**的几条，记录在此避免后续重复怀疑

- **panic 不会触发回滚**（已确认）。gorm 的 `Transaction` 不 `recover`：`panicked` 为 true 时只做 `tx.Rollback()`，然后让 panic 继续 unwind，`Exec` 的 `if err != nil` 根本执行不到。要兜住得在 `Exec` 里加 `defer`+`recover`，但那会把"panic 被吞掉变成普通 error"的语义一并引进来，**超出"补完 todo"的范围，未改**。
- **嵌套事务下回滚仍会被外层回滚掉**（已确认）。gorm 检测到 `db.Statement.ConnPool` 实现了 `TxCommitter` 就改走 SAVEPOINT。若 `this.db` 本身已在事务中，回滚 handler 的写入只是另一个 savepoint，外层一 rollback 照样没了。jotcash 每次 `transaction()` 都是 `open()` 出一个全新连接（`jotcash/db/db.go:224`），当前不踩这个坑。属库级使用约束，未改。
- **第一个 commit handler 就失败时，回滚照样跑**。这是有意的：无论主体写没写进去，"主体没成功"这个事实成立，补偿就该走。若哪天要区分"压根没开始"和"做了一半"，得给 `TransactionHandler` 加状态，不是本轮范围。
- **`Transaction` 对象非并发安全、可被重复 `Exec`**。`AddCommit`/`AddRollback` 是裸 `append`，handler 自身带 `Count`/`Object` 状态。老代码的 `Transaction(ctx, db, handlers...)` 同样如此，非本轮引入。
- **`Transaction` 结构体自身不是 `TransactionHandler`**：`Exec(ctx)` 与接口的 `Exec(ctx, tx)` 签名不同，事务对象不能作为 handler 嵌套进另一个事务。当前无人需要，未改。
- **`NewTransaction(nil).Exec(ctx)` 会 panic**：`this.db.WithContext` 对 nil 接收者直接崩。老代码传 nil db 同样崩，行为未回退。

## 三、实施

### 3.1 生产代码：`util/gorm.go`，净增 23 行，无新增导出符号

最终落地版本（`06a6a68`，在我提交的草案上由你调整了命名与日志位置，逐条复核见 3.3）：

```go
type Transaction struct {
	db           *gorm.DB
	commitHook   []TransactionHandler
	rollbackHook []TransactionHandler
}

func (this *Transaction) Exec(ctx context.Context) error {
	err := this.commit(ctx, this.commitHook...)
	if err != nil {
		logrus.WithContext(ctx).WithFields(logrus.Fields{"err": err}).Error("事务执行，异常")
		this.rollback(ctx, this.rollbackHook...)
		return err
	}
	return nil
}
func (this *Transaction) commit(ctx context.Context, handler ...TransactionHandler) error {
	if len(handler) == 0 {
		return nil
	}
	err := this.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		for i := range handler {
			err := handler[i].Exec(ctx, tx)
			if err != nil {
				return err
			}
		}
		return nil
	})
	if err != nil {
		return err
	}
	return nil
}
func (this *Transaction) rollback(ctx context.Context, handler ...TransactionHandler) {
	if len(handler) == 0 {
		return
	}
	ctx = context.WithoutCancel(ctx)
	err := this.commit(ctx, handler...)
	if err != nil {
		logrus.WithContext(ctx).WithFields(logrus.Fields{"err": err}).Error("事务回滚，异常")
		return
	}
	logrus.WithContext(ctx).WithFields(logrus.Fields{}).Info("事务回滚，完成")
}
```

四条约束的落点（`util/gorm.go:113`/`:122`/`:140`）：

| 约束 | 落在哪 |
| --- | --- |
| R1 另起事务 | `rollback` 转调 `commit`，后者重新 `this.db.WithContext(ctx).Transaction(...)` |
| R2 摘取消信号 | `rollback` 里的 `ctx = context.WithoutCancel(ctx)`（**只在回滚路径上摘，主事务必须继续尊重取消**） |
| R3 回滚错误不顶掉根因 | `rollback` 无返回值，物理上没法把回滚错误抛出去 |
| R4 无 handler 不空开事务 | `commit` 与 `rollback` 各一处 `len(handler) == 0` 短路 |

几处刻意的取舍：

- **`commit`/`rollback` 复用同一段执行逻辑，而不是把循环复制一遍**：两者的执行语义完全相同（同一事务内按序、遇错中断、整体回滚），复制会让两条路径日后各自漂移。抽完之后整段 `Transaction` 代码比改动前只多 23 行。
- **`len(handler) == 0` 的短路 commit 路径也放**：commit 为空时同样不必空开事务，且 jotcash 已经在调用侧手写了这个判断（`jotcash/db/db.go:126` 的 `if len(handlers) > 0`），把它收进库里，下游那行判断就是冗余的了。语义上仍是 no-op，`TestTransaction` 的"空handler事务须正常返回"断言不变。
- **`rollback` 不返回 error**：不是偷懒，是用签名把 R3 钉死——留个返回值，日后总会有人顺手 `return`。
- **主事务根因记在 `Exec` 的 `事务执行，异常` 一行，而不是塞进回滚日志的 `cause` 字段**：两条日志共用同一个 logId（`WithoutCancel` 保值），串得起来；且这条日志在**没有 rollbackHook 时同样会打**，覆盖面比挂在回滚日志上更全。
- **字段命名 `commitHook`/`rollbackHook`**：为了把 `commit`/`rollback` 两个名字让给方法。代价是 `rollback` 内部读起来是"回滚里调 commit"，因是私有方法且仅两个调用点，可接受。

## 五、待确认（不敢替你拍板的两条）

1. **回滚 handler 拿不到失败原因。** `TransactionHandler.Exec(ctx, tx)`（`util/gorm.go:89`）没有 err 入参，回滚 handler 只知道"主事务失败了"，不知道"为什么失败"。若 `AddRollback` 的用途是**失败留痕**（比如 jotcash 的 `model.OperationLog`，`jotcash/db/db.go:88` 那种带 `Result` 字段的记录），那条失败日志里就写不进根因——handler 是在 `Exec` 之前就构造好的，那时还没有 err。

## 六、一句话结论

`9abbf28` **方向对、位置对**：事务对象化之后 commit/rollback 两组 handler 的编排关系确实比原来的变参函数清楚，`//todo` 放在 `Transaction` 返回之后也是**唯一可行**的补偿位置（gorm 在 `fc` 返回时已经 `tx.Rollback()` 并终结了原 tx，闭包里无论怎么写都补偿不了）。
