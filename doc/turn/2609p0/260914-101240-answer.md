# 260914-101240 交付说明

## 一、背景调研

### 1.1 GenId 现状（`util/gen.go`、`util/time.go`）

- `DateLayout_060102150405_0000000 = "060102150405.000000"`（`util/time.go:15`）——常量名写了 7 个 0，实际布局只有 6 位小数，命名与取值本就不一致。
- `GenIdByTime`（`util/gen.go:27`）：按 `E8Loc` 格式化为 `YYMMDDhhmmss.ffffff`，再 `str[:12] + str[13:]` 去掉小数点，得到 **18 位纯数字**，`Str2Int[int64]` 转为 `int64`。
- `GenId`（`util/gen.go:38`）：包级互斥锁保护发号水位 `genIdLock.micro`（**微秒**），`micro <= 水位` 时取 `水位+1`，再回落到 `GenIdByTime(time.UnixMicro(micro))`。补偿发生在**时间域**而非 ID 整数域，所以跨秒/分/时/日/年进位后仍是合法时间（`util/gen_test.go:186-242` 已锁定这一点）。
- `ParseStrId`（`util/gen.go:55`）：不足 18 位左补 0，长度必须等于 18，第 12 位后插回小数点再 `ParseStr2Time`。

**问题**：18 位 ID 量级约 `2.6e17`，JS `Number.MAX_SAFE_INTEGER = 9007199254740991`（约 `9.007e15`，16 位）。ID 经 JSON 传给前端会被 IEEE-754 双精度截断，末位失真。

## 二、Review 结论

### 2.1 已确认的缺陷

**R1（阻断级）`util` 包单测自 2026-09-10 起完全无法编译，零执行。**
`go test ./...` 输出（本次实测）：

```
util/config_test.go:207:10: service.Stop undefined (type *ConfigService has no field or method Stop)
util/gin_test.go:184:2: undefined: ClaimsGin
util/gin_test.go:246:17: not enough arguments in call to ValidateGin
        have (*gin.Context, string)
        want (*gin.Context, string, Claims)
```
（`util/gorm_test.go` 的 `fakeInquiryHandler` 同样停留在旧 `InquiryHandler` 三参签名，因编译器 "too many errors" 截断未列出。）

成因分三层：

1. `ConfigService.Stop` **从未存在**（`git log --all -S "ConfigService) Stop"` 无任何提交），`TestConfigServiceStop`（`b3e7c3c`，09-10 17:36）按"Start 的反向操作"写了用例。
2. `ClaimsGin` 在 `681e08d`（09-10 17:46，即加完用例 10 分钟后）被删除，`TestClaimsGin` 未同步删除。
3. `7b1b8e3`/`37b361c`/`2d06a61` 改了 `ValidateGin`、`Inquiry` 签名，测试未同步——即 prompt 中所说"单测也没有补上"。

**R2（`7b1b8e3` 遗漏）`GetClaims`/`SetClaims` 未随 `ValidateGin` 泛化。**
`ValidateGin` 现在把调用方传入的任意 `Claims` 实现写进 `c.Set(ClaimsKey, claims)`（`util/gin.go:134`），而 `GetClaims`（`util/gin.go:51`）固定断言 `*model.Claims`。调用方一旦使用自定义 claims 类型，`GetCtxValue[T]` 的 `value.(T)` 断言失败**静默返回 nil**（`util/ctx.go:7-11`，忽略 ok），下游 `Ping`（`util/gin.go:47`）打印的 claims 恒为 nil，且无任何报错。

**R3（`7b1b8e3` 遗漏）`ValidateGin` 的 `claims` 入参必须是"每请求新建的指针"，接口签名没有任何约束或说明。**
- 传值（`model.Claims{}`）：能通过编译（三个 getter 与 `jwt.StandardClaims.Valid` 都是值接收者），但 `DeJwt` → `jwt.ParseWithClaims` → `json.Unmarshal` 到非指针会失败，请求恒被 401/500 拒绝；且 `c.Set` 存进去的是 `model.Claims` 值，`GetClaims` 断言 `*model.Claims` 亦取不到。
- 传共享指针（在 `r.Use(...)` 闭包外只 new 一次）：所有请求复用同一 claims 对象，并发下数据竞争 + 串号。

**R4（`a46d12d` 的必要性说明，非缺陷）**：`7b1b8e3` 把局部变量从 `model.Claims` 值改成了 `Claims` 接口，此时旧写法 `&claims` 得到的是 `*util.Claims`（指向接口的指针），`GetClaims` 的 `*model.Claims` 断言必然失败。`a46d12d` 改为 `c.Set(ClaimsKey, claims)` 是对 `7b1b8e3` 引入缺陷的修补，方向正确。

### 2.2 `ValidateGin` 与 `claims.LogId`：跨服务链路追踪已断（已确认并修复）

这是任务 Prompt 追问的一条，结论全部来自 git 历史与代码，逐条给依据。

**Q：现在 `ValidateGin` 开头的 `setGinLogId(c, GetLogId(c))`，`c` 里会有 LogId 吗？**
**A：没有。** 全新请求的 gin 上下文里不存在 `LogIdKey`——全仓库 `c.Set(LogIdKey, ...)` 只出现在 `setGinLogId` 自己内部一处（`util/gin.go:65`），本库没有任何中间件会在 `ValidateGin` 之前写入它。于是 `GetLogId(c)` 恒为 0，`setGinLogId` 必然走 `logId <= 0` 分支用 `GenId()` 现生成一个。已在 `TestValidateGinLogIdFromClaims` 里把这条前提显式断言下来。

**Q：以前 `ValidateGin` 是怎么实现的？是不是从 claims 取 LogId 再 set 到 c 里？**
**A：`ValidateGin` 从来没有做过这件事。** 遍历 `util/gin.go` 全部 12 个历史版本（2023-05-03 `4a73cd2` 至今）逐个抽出 `ValidateGin` 函数体，其中出现 `LogId` 的位置**始终只有开头那一行**：2023 年版是 `setGinLogId(c)`（其内部 `logId := GetLogId(c)`），后来展开成 `setGinLogId(c, GetLogId(c))`，语义一致——**只从 gin 上下文读，从不读 JWT**。

**做这件事的是 `ClaimsGin`，它已被删除。** 删除前（`3646b2a`）的实现：

```go
func ClaimsGin(c *gin.Context, secret string) {
	setGinLogId(c, GetLogId(c))
	defer c.Next()
	...
	var claims model.Claims
	DeJwt(c, token, secret, &claims)
	if claims.LogId > 0 {
		setGinLogId(c, claims.LogId)   // ← 唯一做链路贯通的地方
	}
	c.Set(ClaimsKey, &claims)
}
```

`ClaimsGin` 在 `681e08d`（2026-09-10 17:46）被整体删除，这一行随之消失。

**为什么这是缺陷而不是取舍**：发送端至今仍在往 JWT 里塞 logId——`EnDefaultJwt`（`util/codec.go:82`）第 88 行 `claims.LogId = GetLogId(ctx)`，经 `EnAuthJwt`（`util/codec.go:78`）产出 Authorization 头。`model.Claims.LogId` 的字段注释也写着"在某次调用链中"（`model/http.go:12`）。**发送方付出了代价、接收方却直接丢弃**，调用链在服务边界断开——这种单向不对称只可能是删 `ClaimsGin` 时的连带遗漏，不是有意设计。

**已修复**（改动见 4.1）：`util.Claims` 接口补 `GetLogId() int64`，`ValidateGin` 在**验签通过之后**采纳 `claims.GetLogId()`。放在验签后而非 `ClaimsGin` 那样紧跟 `DeJwt`，有两点好处：只采信签名合法的 logId（伪造 token 无法注入），且后续过期/重放/uri 的拒绝日志也能挂到调用方链路上。

### 2.3 已由任务 Prompt 拍板、不再改动的两项

- **`Inquiry` 钩子错误不在 Handler 内补日志**（原 Q2）：按任务 Prompt 明确指示，`DeleteHandler`/`SelectHandler` 保持裸 `return err`，与 `ConfigService.Start`（`util/config.go:44-46`）"下层已打日志则裸传"的风格一致。**不改动。**

## 三、方案

### 3.1 GenId 改造为 JS 安全

**约束推导**：生成规则必须保留 =「东八区时间按 `060102150405` 格式化 + 亚秒位拼接，纯数字、时间有序、可反解回时间」。日期前缀 12 位是规则的一部分不可动，唯一可调的是亚秒位数 n。

| n | 位数 | 精度 | 容量(个/秒) | JS 安全期 |
| --- | --- | --- | --- | --- |
| 6（原实现·微秒） | 18 | 1µs | 1,000,000 | **无**——约 2.6e17，是安全整数的 29 倍 |
| 3（毫秒） | 15 | 1ms | 1,000 | 永久（上界 991231235959999 仅为安全整数的 11%） |
| **4（0.1 毫秒）** | **16** | **100µs** | **10,000** | **至 2090-07-19 23:59:59.9999** |

**定案取 n = 4**（按任务要求"不需要兼容到 2090"）。相对 3 位方案，容量提升 10 倍、时间前移量减少到 1/10，代价是安全期有终点。

**安全期边界是精确算出来的，不是取整**：JS 安全整数 `9007199254740991` 落在 2090 年 7 月中旬。
- 最后一个安全 ID：`9007192359599999` = 2090-07-19 23:59:59.9999 < 9007199254740991 ✅
- 第一个越界 ID：`9007200000000000` = 2090-07-20 00:00:00.0000 > 9007199254740991 ❌

（初稿曾按"年份上界 99"保守地写成"2089 年起越界"，实际 2089-12-31 与 2090-01-01 都仍安全，边界在 2090-07-20。`TestGenIdJsSafe` 已把这两个值双向断死。）

**改动点**：

1. `util/time.go`：`DateLayout_060102150405_0000000 = "060102150405.000000"` → `DateLayout_060102150405_0000 = "060102150405.0000"`。常量名随取值一起改，避免沿用"7 个 0 / 6 位小数"的错误命名。
2. `util/gen.go`：
   - 新增 `const IdLen = 16`（含安全期边界的注释）与 `const IdTickMicro = 100`（亚秒位精度，单位微秒）。
   - `GenIdByTime` 的 `str[:12] + str[13:]` 保持不变（12 位日期 + 1 位小数点 + 亚秒位，切片下标无需调整）。
   - 发号水位 `genIdLock.micro`（微秒）→ `genIdLock.tick`（100 微秒），取值 `time.Now().UnixMicro() / IdTickMicro`，回落 `time.UnixMicro(tick * IdTickMicro)`。**必须同步**：水位若仍按微秒累加，同一个 100 微秒窗口内的连续调用会产出完全相同的 ID。
   - `ParseStrId` 的长度校验与左补零改用 `IdLen`。
3. 单测同步：`util/gen_test.go`、`util/log_test.go`、`util/gin_test.go`、`util/transform_test.go`。
4. `util/gen_test.go` 的 `TestGenIdUnique`/`TestGenIdUniqueConcurrent` 增加水位还原 `t.Cleanup`：批量发 2 万个号会把包级水位推到未来 2 秒，而 `util/log_test.go:104` 断言 `ParseId(GenId())` 与当前时刻偏差在 1 分钟内，不还原会因用例执行顺序偶发失败。

### 3.1.1 发号容量与"数组循环赋值"的实测结论

**容量 = 10,000 个/秒**（1 秒 ÷ 100 微秒）。

**够不够用，取决于批量大小，而不是"快不快"**——关键在于 `GenId` 本身的执行速度远高于它的时间预算。实测（本机，`GenId` 顺序调用）：

| 循环元素数 | 循环耗时 | 实测调用吞吐 | 末位 ID 内嵌时间前移 |
| --- | --- | --- | --- |
| 100 | 320µs | 31.2 万/秒 | 10ms |
| 1,000 | 3.0ms | 33.3 万/秒 | 97ms |
| 5,000 | 14.4ms | 34.8 万/秒 | 486ms |
| 10,000 | 28.5ms | 35.1 万/秒 | 971ms |
| 100,000 | 300ms | 33.3 万/秒 | 9.7s |

`GenId` 能跑到约 **33 万次/秒**，是 1 万/秒时间预算的 **33 倍**。所以只要是紧凑循环，水位必然被顶到未来，前移量≈ `元素数 ÷ 10000` 秒：

- **千级以内（≤1000 个）：前移 ≤ 0.1 秒，可忽略——够用。**
- 万级（10000 个）：前移约 1 秒。
- 十万级：前移约 10 秒。

**前移是自愈的**：停止发号后，真实时间追上水位即回归（`tick = max(当前时刻, 水位+1)`），不会累积。

**这个上界是结构性的，无法再优化**：补偿式发号取 `max(当前时刻, 水位+1)` 已经是"严格递增的时间编码 ID"能做到的最小前移——每个 ID 必须占用一个不同的时间刻度，n 个 ID 就必然占用 n 个刻度。**真正的调节杆只有精度**：从 3 位改到 4 位，前移量已经降到 1/10；若要再降一个数量级就得上 5 位，而 5 位（17 位 ID，最大 9.9e16）直接越过 JS 安全整数，与本次目标冲突。若将来确有十万级批量且不容前移，需要换号段式 ID（预分配区间），而不是继续加亚秒位。

## 五、影响与注意事项

1. **ID 位数由 18 变 16。** 已落库的历史 18 位 ID 无法再被 `ParseStrId` 解析（`TestParseStrId` 已把这条显式断言进去）。按任务 Prompt 确认，**不存在依赖"从 18 位历史 ID 反解时间"的线上数据，该风险已出清。**
2. **安全期有终点：2090-07-20 00:00:00 起 ID 越过 JS 安全整数。** 这是按"不需要兼容到 2090"自觉接受的取舍，`TestGenIdJsSafe` 已把边界双向断死，将来若需跨过它会被用例明确提示。
3. **单进程发号容量 10,000 个/秒**，前移上界 = 元素数 ÷ 10000 秒（详见 3.1.1）。故给批量发号的用例加了包级水位还原，否则 `util/log_test.go:104` 的"解析时间与当前偏差须在 1 分钟内"会随用例顺序偶发失败。
4. `DateLayout_060102150405_0000000` 已改名为 `DateLayout_060102150405_0000`，仓库外的引用方需同步。
5. **`util.Claims` 接口新增 `GetLogId() int64`，是不兼容变更**：仓库外自定义 claims 类型的服务须补这一个方法才能编译。该接口 2026-09-13 才引入（`7b1b8e3`），下游铺开面应当很小；且它与既有的 `GetExpiresAt/GetReqId/GetUri` 完全同构，不引入新概念。
