# 260914-171040 交付说明

## 一、背景调研

### 1.1 被review的改动

本次review对象是 `e0a51ff`（2026-09-14 17:11:40，与本轮 prompt 时间戳一致）对 `util/config.go` 的改动，共四处：

| # | 改动 | 目的（由代码推断） |
| --- | --- | --- |
| A | `ConfigService` → `ConfigService[Config any]`，新增字段 `config Config` | 把配置对象收进服务自身 |
| B | 新增 `GetConfig(ctx) Config`，读锁保护 | 对外提供并发安全的配置读取 |
| C | `lock` 由 `*sync.Mutex` 改为 `*sync.RWMutex` | 配合 B，读多写少 |
| D | `flushConfig` 前补空行 | 排版 |

### 1.2 下游用法（判断改动意图的关键依据）

`jotcash/config/config.go` 是本仓库外唯一在用 `ConfigService` 的工程（全盘 grep `NewConfigService|ConfigHandler` 的结果）。它的 HEAD 版本（`dd2183e`）是这样的：

```go
var configService *util.ConfigService
var confLock sync.RWMutex          //每个下游各自重复一遍的样板
var conf model.Config

func GetConfig() model.Config { confLock.RLock(); defer confLock.RUnlock(); return conf }

func (this *ConfigHandler) Parse(ctx context.Context, text string) error {
	...
	confLock.Lock()
	defer confLock.Unlock()
	conf = config          //配置对象存在下游自己手里，ConfigService 完全不知情
	return nil
}
```

该文件当前工作区还有一份未提交改动，把 `confLock + conf` 换成了 `atomic.Pointer[model.Config]`，但 `Parse` 里仍是 `conf = config`（类型不匹配，**该文件目前编译不过**）。

**结论（已确认）**：`e0a51ff` 是在把「锁 + 配置变量 + GetConfig」这套每个下游都要重抄一遍的样板，上收到 `util.ConfigService[Config]` 里。

## 二、Review 结论

### 2.1 C1（致命·已修复）`config` 字段没有任何写入点，锁保护的是一个永远为零值的字段

`e0a51ff` 只加了字段 A 和读取口 B，**没有加写入口**：改动前后 `ConfigHandler.Parse` 的签名都是 `Parse(ctx, text) error`，只回传错误、不回传配置对象；`loadConfig` 拿到的也只有 `err`。全文件对 `this.config` 仅有一次引用，就是 `GetConfig` 里的那次读。

后果分两层，第二层才是真正的并发问题：

1. **功能层**：`GetConfig` 恒返回 `Config` 的零值。
2. **并发层**：配置对象实际仍存在各下游自己的包级变量里（`jotcash/config/config.go` 的 `conf`），由守护协程 `flushConfig` 写、业务协程读。下游一旦按新接口的字面承诺「配置已由 ConfigService 加锁托管」去掉自己那把 `confLock`，写方（守护协程）与读方（业务协程）之间就**再无任何同步**——而 `GetConfig` 又会一直返回零值把问题掩盖成「配置没生效」而不是崩溃。这把「读到零值」和「数据竞争」两件事叠在了一起。

`ConfigService` 是被多个工程引用的基础库，这个口子会在每个接入方身上各复现一次。

### 2.2 C2（已确认·按取舍保留，以注释约束）写锁覆盖文件IO与handler回调

`LoadConfig`（`util/config.go:87`）在整个加载流程上持写锁，锁内包含 `ReadFile2Str`、`WriteStr2File` 两次磁盘IO与 `GetDefault`/`Parse` 两个 handler 回调。带来两个已确认的性质：

- **读方会被加载流程阻塞**：`GetConfig` 的读锁要等整个「读文件 + 解析」结束；Go 的 `sync.RWMutex` 写者优先，等待中的写锁还会把后续 `RLock` 一并挡住。
- **`Parse` 不可重入**：`sync.RWMutex` 不可重入，`Parse` 实现内若回调 `GetConfig`（`RLock`）或 `LoadConfig`（`Lock`）即**自锁**。改动前 `ConfigService` 没有任何读取口，handler 没有理由回调服务；B 加上 `GetConfig` 之后，这条路径第一次变得「看起来可以走」，所以这是本次改动新引入的隐患。

按本轮明确要求「只用一把锁、保持原函数结构、不新增函数」，此项**不改代码结构**，改为在 `ConfigHandler.Parse` 的接口注释里把约束写死（`util/config.go:15-17`）。取舍依据见 3.2。

### 2.3 C3（已确认·已随C1修复）解析失败时的发布时机

`loadConfig` 原本在 `Parse` 成功后才 `this.text = text`，解析失败不推进水位——方向是对的。C1 修复后必须保证 `text` 与 `config` **一起发布**：只要有一个先写，失败路径上就会出现「文本已推进、配置还是旧的」或反之的错配，且因为 `text` 是「是否需要重新解析」的唯一判据（`util/config.go:107`），错配会被一直带到下一次文件变更为止。现改为两行相邻赋值，在同一个写锁临界区内完成（`util/config.go:116-117`）。

### 2.4 C4（已确认·已修复）`util` 包因该改动再次整包编译失败

`e0a51ff` 把 `NewConfigService` 改成泛型后，`Config` 无法从 `NewConfigService(h)` 的实参推断：

```
vet: util/config_test.go:56:13: in call to NewConfigService, cannot infer Config (declared at util/config.go:18:23)
```

`util` 包连同全部 239 个用例再次 0 执行（与上一轮 `260914-101240-answer.md` 第 2.1 节记录的同类问题重复出现）。C1 的修复顺带解决了它，理由见 3.1。

### 2.5 复核过但**不构成**缺陷的几条

逐条走查后排除，记录在此避免后续重复怀疑：

- **`Start` 持锁创建守护池会不会自锁**：`NewDaemonSingleGoPool` → `ants.Pool.Submit` 把任务交给 worker 协程后立即返回，不等待任务执行（`util/sync.go:130`）。守护任务首轮 `LoadConfig` 会阻塞到 `Start` 释放锁为止，不形成环。代价只是启动时多读一次配置文件（文本未变，不会重复解析）。
- **`Stop` 持锁关闭协程池会不会与守护协程形成锁序反转**：`Stop` 的持锁顺序是 `ConfigService.lock` → `SingleGoPool.lock`（`util/sync.go:228`），守护任务重启路径的顺序是 `SingleGoPool.lock` → `Submit`。要成环需要「一个协程阻塞在 `Submit` 上等 worker，同时 worker 被另一个阻塞在 `ConfigService.lock` 的任务占着」；而单协程池容量为 1、重启协程只在上一个任务**已退出**后才发起 `Submit`，两者不能同时存在。**不成环。**
- **`ants.Pool.Release` 是否会等待运行中的任务**：不会（等待的是 `ReleaseTimeout`），`Stop` 不会因守护任务正在加载而卡住。
- **`GetConfig` 返回值拷贝**：返回的是 `Config` 的浅拷贝。服务每次都整体替换配置对象、不原地改动，因此只要 handler 每次 `Parse` 都新建对象，读方之间就不会共享可变状态。该约束已写进接口注释（`util/config.go:16`）。

## 三、方案与取舍

### 3.1 C1 的修复：把 `ConfigHandler` 泛型化，由 `Parse` 回传配置对象

```go
type ConfigHandler[Config any] interface {
	GetPath(ctx context.Context) string
	GetDefault(ctx context.Context) string
	Parse(ctx context.Context, text string) (Config, error)   //← 唯一的签名改动
}
```

**为什么只能是这条路**：`config` 字段要被写，值只可能来自解析配置文本这一步，而这一步的唯一入口就是 `handler.Parse`。备选方案各自的否决理由：

| 备选 | 否决理由 |
| --- | --- |
| 给服务加 `SetConfig`，由 `Parse` 内部回调 | `Parse` 在写锁内执行，回调 `SetConfig` 再抢同一把锁即自锁；且 handler 需要反向持有 service 引用，构造期成环 |
| 删掉 `config`/`GetConfig`，退回下游各自存 | 与 `e0a51ff` 的意图相反，且每个下游继续重抄一遍锁样板 |
| 服务改收 `parse func(ctx, text) (Config, error)` | 与既有 `ConfigHandler` 接口风格不一致，且 `GetPath`/`GetDefault` 仍要走接口，变成两套入参 |

**顺带解决 C4**：Go 1.21 起，实参赋给参数化接口时可从**方法签名**反推类型实参（本仓库 `go 1.27`）。`Parse` 回传 `Config` 后，`NewConfigService(new(ConfigHandler))` 能从 handler 的 `Parse` 方法推断出 `Config`，**调用方一行都不用改**。已单独写最小样例实测确认（`*main.Service[main.myConf]`）。

### 3.2 C2 的取舍：维持单锁与原函数结构，把约束写进接口注释

初版实现曾把「文件IO + handler 回调」移出锁外、只在锁内做两行赋值（并一度引入第二把锁串行化加载流程），可同时消除「读方被阻塞」与「`Parse` 不可重入」两项。经本轮明确要求**只用一把锁、保持原函数结构、不新增函数**后回退，最终按下表取舍：

| 维度 | 保持原结构（采纳） | 加载流程移出锁外（放弃） |
| --- | --- | --- |
| `util/config.go` 改动量 | **11 增 5 删，无新增函数** | 36 增 14 删，新增 3 个函数 |
| C1 数据竞争 | **已消除**（写在写锁内、读在读锁内） | 已消除 |
| 读方在加载期间 | 被阻塞（一次文件读 + 一次解析，默认 1 分钟一轮） | 不阻塞 |
| `Parse` 内回调 `GetConfig` | 自锁 → **以接口注释约束** | 允许，读到上一份配置 |

**依据**：C1 才是本次review要找的并发问题（数据竞争 + 恒零值），单锁原结构已把它修干净；C2 是「阻塞时长」与「重入约束」，属可用文档约束住的性质问题，不是竞争。配置文件通常在 KB 级、重载周期一分钟一次，读方被挡住的时间是毫秒级。

**代价必须显式记住**：`Parse`/`GetDefault` 的实现里**不能**出现对 `GetConfig`/`LoadConfig` 的调用，否则死锁；已写在 `util/config.go:15-17` 的接口注释里。若将来某个下游的 `Parse` 确实需要读上一份配置，再按放弃的那个方案改造。

## 五、影响与注意事项

1. **`ConfigHandler.Parse` 签名变更，是不兼容改动**，下游必须改：`func (this *ConfigHandler) Parse(ctx, text) error` → `(model.Config, error)`，函数体末尾的 `conf = config` 改为 `return config, nil`，同时删掉下游自己的 `conf`/`confLock`/`GetConfig`。调用侧 `NewConfigService(new(ConfigHandler))` **无须改动**（类型自动推断）。
2. **`jotcash` 需要同步改造**：`jotcash/config/config.go` 当前工作区那份未提交改动本身就编译不过（`conf = config` 赋给 `atomic.Pointer[model.Config]`），改造后可整体删除 `atomic.Pointer` 与包级 `conf`，`config.GetConfig()` 转发到 `configService.GetConfig(ctx)` 即可。**本轮未改动该仓库**（不在交付范围内，且是另一个 git 工作区）。
3. **`Parse` 与 `GetDefault` 的实现内不可调用 `GetConfig`/`LoadConfig`**，否则死锁（2.2、3.2）。已写进接口注释。
4. **`Parse` 每次必须新建配置对象**，不可原地改动已返回过的对象，否则读方会读到改了一半的配置（服务只做整体替换，不做深拷贝）。
5. 未提交任何 git 变更（按流程要求），临时文件已清理。
